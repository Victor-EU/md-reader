# ADR 0013: WP 1.8 Settings, session, single instance, associations

Status: accepted, 2026-09-08. Covers the two JSON files the app keeps for
itself, session restore, the routing of files the OS hands us, the
before-close round trip, and the file associations.

## One store, two speeds

`crates/core/src/state.rs` holds the newest value in memory and lets at
most one write an interval reach the disk. Everything that needs the
value now — the router that decides which window a file belongs to, the
flush a close performs — reads it from memory and never waits for the
disk.

The write itself is `atomic::replace`, the same one a document save uses.
That is not a nicety: the session file is what a launch trusts, so a
crash in the middle of one has to leave the previous session rather than
half of the new one. Truncating the file by hand and launching gives a
blank window and a `session.json.bad` beside it, which is the recovery
path for the case atomicity is supposed to prevent.

The store's lock is held across the write. Two writers could otherwise
each take a value and race their renames, and the older one could land
last. The cost is that a `set` from a command handler can wait out one
small atomic write, which the throttle keeps rare.

## Why the shell debounces too, and why not evenly

The shell has its own pause before it pushes, and the two throttles are
not redundant. The store's job is the disk; the shell's is
serialization, because an untitled document's whole text is in the
session and a keystroke would otherwise serialize it.

That is the only expensive change, so it is the only one that waits.
A tab opening, a mode changing, the sidebar coming out — those are
pushed at the end of the turn. The reason is macOS: Cmd+Q goes through
`NSApplication.terminate:` and reaches the app only as `RunEvent::Exit`,
with no window close and no exit request, far too late to ask a webview
for anything. What the window has already said is all that survives it,
so it should be as close to the truth as it can cheaply be. Measured in
the real app: a tab switch made immediately before Cmd+Q is in the file;
before this split it was not.

Giving Cmd+Q the same round trip means owning the macOS menu, because the
predefined Quit item is what bypasses the event loop. That is the
platform work of build plan section 8, and it is where the last of this
gap closes — the residual today is text typed into an untitled document
in the half second before a Cmd+Q.

## The round trip a window close does get

A window close is stopped once. The window hears `before-close`, writes
down what it holds, and calls `confirm_close`, which closes it for real.
Today that is the session; from WP 1.11 it is also an autosave still
waiting on its timer, which is what the round trip exists for. A window
that never answers is closed when the grace period runs out, because a
wedged webview must not be able to keep the app open.

`RunEvent::ExitRequested` asks the same question of every window and
holds the quit until they answer. On macOS that fires only after the last
window has closed, with nothing left to ask; it is the platforms where
quitting and closing are one gesture that need it.

## Files the OS hands us, and where they land

A file goes to the window that already has it open, and anything else to
the window in front. That is the registry design 6.5 asks for, and the
session is the registry: `save_window` is both what the next launch
restores and what the router reads. There is no second bookkeeping to
keep in step, and the value is current the moment the command returns.

Between the OS and the window there is a queue, because the two are not
ready at the same time. Draining it is also how a window says it is
listening: after that the same files arrive as an event. Without the
queue a launch document is lost to a listener that is not attached yet;
without the readiness flag it is opened twice by one that is.

The queue is not enough on its own. macOS sends the open event for a
launch document **before `setup` runs** — before there is any state to
put it in. Verified by watching a cold launch: `RunEvent::Opened`, then
`setup`. So the paths land in a `static` that exists before the app does,
and `start` hands them on once it has somewhere to put them. Restore
runs first and the launch files second, so double-clicking a file that
was already open focuses its tab instead of opening a second one.

## Single instance where the OS does not provide it

`tauri-plugin-single-instance` is registered on Windows and Linux and not
on macOS, where a bundled app is already one instance and the files
arrive as an Apple event. The one path this leaves is running the binary
directly from a macOS terminal while the app is open, which starts a
second process; that is a developer's path, not a reader's. Windows is
written to the documented callback and left for the parked Windows gate.

## Restoring a document, and what a restored document is

A file is read again from disk; only an untitled document is carried in
the session file, because losing it would lose the only copy of it. A
file that is no longer there is left out rather than restored empty — a
tab that looks like the document but holds nothing is a lie about it —
and the status bar names it.

A restored untitled document has an empty base, so the dirty dot stays
on it. The by-hand pass is what found this: with the base set to the
restored text, the tab came back clean and the buffer looked as though
some file held it. Nothing does. `reviewed` is left where the document
is, though, because the reader has already read it and the Changes badge
is about what happened since they looked.

## The window's frame belongs to Rust

The webview does not know where its window is, so `save_window` reads the
frame itself and `label` and `bounds` never cross the IPC. A frame with
no screen under its title bar keeps its size and takes a fresh position:
a window restored onto a monitor that has since been unplugged is one the
reader can neither see nor move.

The windows start hidden and are shown once they are placed, so nobody
watches one appear at the default position and jump.

## Settings, thin on purpose

The design names exactly one preference so far — autosave, on, because
the file on disk is the channel to the AI. This work package is the file,
the round trip and somewhere current for it to live; the theme and
typography fields arrive with WP 1.9 and WP 1.11 is what reads autosave.
Both are one `#[serde(default)]` field away, which is also what lets an
older session file survive a newer app.

Nothing in the window changes a setting yet, so `settings.json` is not
written by an ordinary session. The store's round trip is covered in
Rust and the shell's path through `updateSettings` in the browser tests.

## Tabs point into a document list

The session's documents are a list and its tabs name one by index, so two
views of one document restore as two tabs on one buffer with shared undo
rather than as two buffers that drift apart. An index out of range drops
that tab and nothing else.

Positions are UTF-16 offsets, like everything else on this IPC, and the
scroll position is a source offset rather than a pixel: a character
survives a change of window width. Both are clamped to the document on
restore, because the file may have changed since.

## File associations

`.md`, `.markdown` and `.mdx` are declared in the bundle config, with
role `Editor` and rank `Default` — an opener of markdown, not its
`Owner`, and not demoting ourselves to `Alternate`. Which app actually
handles a double-click is the reader's binding to make; what this
registers is that we are in the list.
