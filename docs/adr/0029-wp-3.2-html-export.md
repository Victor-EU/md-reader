# ADR 0029: WP 3.2 HTML export

Status: accepted, 2026-09-10. One file, the reader's own theme inlined,
the images inside it until there are too many of them.

The plan's line is the whole specification: "Same renderer as Read mode,
inlined CSS from the current theme, images embedded or copied alongside.
No PDF." Design section 12 puts it in the same sentence as the things
that wait: "Export to PDF or DOCX. HTML export is cheap and included; the
others wait."

What an export is for decides most of the rest. It is not a backup — the
file already is one, and it is markdown. It is a copy to hand to somebody
who does not have this app, and probably by mail or by chat. So the thing
to optimise is that it opens and reads correctly on a machine that has
nothing: no stylesheet to fetch, no fonts to install, no folder of
scripts, and no network.

## The same renderer, over the whole document

Read mode renders a screenful at a time and takes blocks out of the page
again when the reader scrolls past them (plan WP 2.7). That is exactly
right for a window onto a ten-megabyte file and exactly wrong to save:
what is in the page at any moment is a screenful and two margins.

So the export renders the document itself. `renderDocument` over a parse
of the whole buffer, the DOM adapter Read mode mounts, and then the same
three enhancers — Shiki for fences, KaTeX for formulas, Mermaid for
diagrams. Same renderer, same parse: `parser.parse` is what the editor's
language extension is built on, so a headless render and the window agree
by construction rather than by test.

The document is built in the window rather than in a fragment, out of
sight behind `position: absolute; left: -99999px; visibility: hidden`.
That is not decoration: all three enhancers check `isConnected` before
they write to an element, and Mermaid measures text to lay a diagram out.
A detached fragment would have come back with the fences uncoloured and
the diagrams unlaid. The host is removed in a `finally`, so a throw in
the middle of an enhancer does not leave it in the page.

`enhancer.run` grew a promise for this. Read mode still does not wait for
it — a slow diagram must not hold up a page that is already legible
without it — but an export is finished only when every fence, formula and
diagram is.

## Formulas come out as MathML

The one place the export deliberately renders differently. KaTeX's HTML
output is spans positioned against KaTeX's own stylesheet and its own
fonts: twenty kilobytes of CSS and about a megabyte of woff2 across sixty
files. A page that stands on its own can carry neither. Its MathML output
is the browser's own business and needs nothing at all.

Same engine, same source, one option — passed per run rather than per
enhancer, because the loaded module, the highlighter and its grammars are
the same either way and an export should not mean a second copy of them.

Fences needed no such trick. Shiki here names its tokens rather than
colouring them (plan WP 2.6), and the names resolve against variables the
exported page already carries.

## `read.css`

"Inlined CSS from the current theme" was two problems wearing one coat.

The rules were the first. They lived in the middle of `app.css`, between
the sidebar and the find bar, and most of that file dresses an app that
an exported page does not have — including `html, body, #app { height:
100% }`, which would have broken scrolling outright. So the rules that
dress a rendered document are now `read.css`, imported by `app.css` and
inlined by the export. One file, so a change to what a callout looks like
changes both, and there is no second copy to drift. Two of its rules
dress controls rather than the document — the fold arrow on a heading and
a fence's copy button — and they stay, because splitting a stylesheet by
which piece of code built which element is a worse seam than carrying ten
dead rules.

The colours were the second. The generated stylesheet carries all four
themes and chooses between them with three attributes a script writes
onto the root element; an exported page has no script and nothing
arriving a moment later. `pageCss(theme, appearance, paper)` is the same
three functions that generate that stylesheet, with the choice already
made, emitting one `:root` block. So a colour added to a palette reaches
an export without anyone having to remember it — and the high-contrast
black paper still comes out as a dark page in a light window, because
that resolution is the palette's rule and not a selector's.

What is not inlined is the fonts. Three variable faces are megabytes; the
families are declared with the system stacks design 11 keeps behind them
for exactly this, so a machine with Inter installed renders identically
and one without falls through to its own sans.

## The images, and where the decision is made

The frontend cannot read a file. The webview's content policy is
`default-src 'self'`, which covers `connect-src`, so even the asset
protocol is not fetchable from a script — and widening that policy to
make an export convenient would be paying for a feature with the app's
one real boundary.

So the frontend renders the page with a numbered sentinel in every `src`
it cannot answer for, hands Rust the page and the list of paths, and Rust
puts the answers in. Nothing parses HTML on the Rust side; it finds the
sentinel, reads the number after it, and writes an escaped URL in its
place. This also means the bytes never cross the bridge: a page with four
megabytes of photographs in it is built where the photographs are.

Under four megabytes of images they go inside the page as `data:` URLs —
base64 is a third bigger again, so that is a page of about five and a
half megabytes, large for something to mail and small for something to
open. Over it they are copied into `<name>-images/` beside the page. One
decision per export rather than a mixture, because the outcome a reader
has to care about is binary: one thing to send, or two.

The page is written before a single image is copied. A failure then
leaves a page whose images are missing, which is visible and fixable; the
other order leaves a folder of images beside a file that was never
written, which is litter.

Three smaller rules, each earning its place:

- The media type comes from the bytes, not from the name — the same rule
  that keeps the `assets` folder honest (design 8). Bytes that are not an
  image cannot be given a media type and so are not carried.
- An image the asset protocol has not been opened to is not read. Read
  mode could not have shown it either, and an export is not a way around
  the fence design 8 puts around a document's folder. The app replaces
  such a path with its own file name, and a path that is not absolute is
  never touched by the filesystem at all.
- A copied name is percent-encoded for the `src` and kept as it is on
  disk, so `my notes.png` is both reachable and still called that.

One unreadable image is counted, not raised. The status line says how
many; a whole export does not fail because one file moved.

## What the reader gets

What they are looking at. Their theme, their paper, their measure, their
size, and the comments shown or folded away as they have them (design
4.3). Not the chrome, because there is no app around the document; not
the controls, because a copy has nothing behind them to act on — the
copy button is gone and a task box is disabled rather than clickable; and
not `data-from`/`data-to`, which is two attributes on every element and
most of a megabyte on a large document, read by nothing outside the app.

The palette command asks where to put it, which is the second of the two
dialogs design 4.5 allows. Everything else it has to say goes in the
status bar: how many images travelled inside the page, or which folder
they went into, or how many could not be read.

## What was left

- **Links between documents.** A relative link to another markdown file
  is written out as it stands and will not resolve beside the exported
  page. Rewriting them would mean deciding what a link to a file nobody
  exported should point at, and there is no answer that is right more
  often than leaving it alone.
- **No table of contents, and no print stylesheet.** The plan asked for
  neither. A print stylesheet is the obvious next thing if anyone ever
  wants paper out of this, and it is where "no PDF" stops being a
  limitation.
- **The four-megabyte line is a number, not a measurement.** It is
  defensible rather than derived. If exports start being surprising in
  either direction, this is the knob.
- **A remote image the reader has allowed stays a remote URL.** The page
  fetches it when it is opened, which is the same bargain design 8 made
  in the window, made again by whoever opens the file. Fetching it at
  export time would be the app making a network request on a document's
  say-so, which is the thing design 8 exists to prevent.
- **A diagram carries the palette Mermaid was first loaded with.** Not
  new here: `initialize` is once per session and bakes the colours into
  the SVG, so Read mode has the same seam when the paper changes after a
  diagram has been drawn. An export made after that switch inherits it,
  which is where it is most visible — light boxes on a black page.
- **Nothing warns before a very large export.** A ten-megabyte document
  with a hundred fences is a few seconds of Shiki, and all the status bar
  says in the meantime is `Exporting…`.
