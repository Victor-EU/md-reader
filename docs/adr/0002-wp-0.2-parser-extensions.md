# ADR 0002: WP 0.2 parser extensions

Status: accepted, 2026-09-07. Covers `packages/markdown` after WP 0.2.

## One dialect list, CommonMark base

`@mdreader/markdown` exports `extensions`, the whole dialect on top of
CommonMark: GFM, then Frontmatter, Callout, Math, Highlight. `editor-core`
now builds its language from `commonmarkLanguage` plus that list, not from
`markdownLanguage`, because the latter bundles Subscript, Superscript, and
Emoji, which design 5.1 leaves out and the headless parser did not have.
`editor-core` keeps the one thing it lost, the table folding rule. A test
in `state.test.ts` dumps both trees for a document using every construct
and asserts they are identical.

## Node shapes

| Construct | Nodes |
|---|---|
| `==text==` | `Highlight(HighlightMark, ..., HighlightMark)` |
| `$x$`, `$$x$$` in a paragraph | `InlineMath(MathMark, MathMark)`; the marks are one or two characters, two means display mode |
| `$$` block | `BlockMath(MathMark, MathContent..., MathMark?)`; container markers such as `QuoteMark` sit between content pieces |
| `> [!type]` | `Blockquote(QuoteMark, CalloutHeader(CalloutMark, CalloutType, CalloutMark, CalloutFold?, CalloutTitle?), ...)` |
| `---` at document start | `Frontmatter(FrontmatterMark, FrontmatterContent?, FrontmatterMark)` |
| `<!-- kind: text -->` | Stock `Comment` or `CommentBlock`; `annotations()` classifies without changing the tree |

Content nodes (`MathContent`, `FrontmatterContent`) exist so a consumer
reads the formula or YAML by concatenating them, never by slicing the
outer range, which would include blockquote markers. They also give a
future `parseMixed` overlay something to target, the way `CodeText` does.

## Callouts stay blockquotes

The plan calls a callout "a refinement of blockquote", and that is taken
literally: the node is a `Blockquote` whose first child is a
`CalloutHeader`. A separate `Callout` node type was rejected because
`@codemirror/lang-markdown`'s Enter handling continues `> ` only inside a
node named `Blockquote`, and losing that inside callouts would be the
opposite of delight. Renderers check for the header child.

The header line consumes the rest of its line, so `[!note]` never becomes
a paragraph. The type is matched with `[A-Za-z0-9_-]+` and must be
followed by whitespace or the end of the line, so `[!not a callout]` and
`[!bug]no` are ordinary quotes. Case is preserved in `CalloutType`; the
renderer lowercases.

## Math follows Pandoc, with one honest deviation

Inline math uses Pandoc's `tex_math_dollars` rules exactly, including the
consequence that `$x$1 ... $y$` scans past the invalid closer to the next
valid one. That is what Pandoc does and the fixture pins it.

Block math ends at a blank line, like Pandoc's display math. Unlike
Pandoc, an unclosed `$$` does not fall back to prose: it becomes a
`BlockMath` with a single `MathMark`, ending at the blank line, the end of
the enclosing container, or the end of input. A block parser cannot give
back lines it has consumed, and building a fake paragraph from them would
differ from the stock parse in other ways (a `- ` line inside would have
started a list). The missing closing mark is the signal for WP 0.3 to
show such a block as source rather than a formula.

`$$` at the start of a line interrupts a paragraph, as a code fence does.
Models write "The equation is:" followed directly by a `$$` line, and
treating that as inline display math inside the paragraph would make the
block widget and the leaf-block extraction miss the most common case.

## Frontmatter looks ahead

Only a closed block is frontmatter. An opening `---` with no `---` or
`...` line anywhere below stays a horizontal rule, so a document does not
turn into a properties panel while the user is typing the block. This
needs a lookahead, which the block parser API does not provide: once
lines are consumed there is no rewind. `internals.ts` reads the parse
context's input, a field the type declarations hide, and scans in 4 KB
chunks until the first closing line. If the field is ever missing the
parser recognizes no frontmatter at all, and the `frontmatter` fixture
snapshot fails, which is the intended alarm.

The same file reads `Line.depth`, which the stock `FencedCode` and
`HTMLBlock` parsers use to notice that a blockquote or list item has
ended. Without it a math block inside a quote would swallow the paragraph
after the quote. The `math-block-container` fixture pins this.

Both are the only places the package touches undeclared fields, and both
are pinned to `@lezer/markdown ~1.7.2`.

## Comments

Verified: a comment inside a paragraph is a `Comment`; one starting a
line is a `CommentBlock` that runs to the end of the line holding `-->`.
Text after `-->` on that line is inside the block, so such a block is not
classified. The app writes block comments on their own line. Kinds are
matched case-insensitively and normalized to lowercase, since models
sometimes capitalize; the app always writes lowercase.

## Line endings

The parser splits on `\n` only, so with CRLF input every `\r` is part of
the preceding line. `MathContent` and `FrontmatterContent` therefore end
in `\r` on such input; consumers trim. Inside the editor this never
happens because CodeMirror normalizes to LF. The `crlf` fixture pins the
positions.

## Tests

- Fixture snapshots: `fixtures/*.md` with a reviewed `fixtures/*.tree`
  beside each, rendered by `dumpTree`. A diff there is a parser change.
- Rule tables per extension, including the Pandoc dollar cases.
- Property tests with fast-check: parsing never throws and always yields a
  well-formed tree for raw strings up to 4 KB and for a soup of dialect
  tokens; and an incremental parse after a random edit equals a parse
  from scratch, which is what the editor relies on every keystroke.
