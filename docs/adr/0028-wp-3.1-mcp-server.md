# ADR 0028: WP 3.1 The MCP server

Status: accepted, 2026-09-09. Streamable HTTP on `127.0.0.1`, a token in
a file only the owner can read, and five tools that ask the window.

The plan's lines are an `rmcp` server "over streamable HTTP on
`127.0.0.1`, random port, bearer token", an endpoint file in app data
with owner-only permissions, a `--mcp-stdio` bridge on the app binary
because "most MCP clients are configured with a stdio command", the five
tools and the `doc://` resources of design section 9, a `write_document`
that "goes through the external-change path with the agent name as
author", and a status bar that "shows the connection".

Design 9 says why any of it exists. The clipboard and the file on disk
already give the reader's work back to a model. What this adds is the two
things neither of them can have: a highlight becomes something an agent
can query, because `==mark==` in a file is a string and an annotation
record is a fact; and a write becomes attributable, because an agent that
says its name over a socket is a name we can put on a version, where a
program that writes a file is anonymous by construction.

## The server asks the window

Four of the five tools are questions about a buffer: what it holds now,
what the reader marked in it, what changed in it since a version. None of
those live in Rust. The buffer is the editor's, and the annotations and
the blocks come out of a Lezer parse tree that only the frontend has.

So the server asks. `Desk` is the whole of what the tools can do to this
machine — five methods — and the Tauri implementation of it emits an
addressed event to the window that has the document open and waits on a
`oneshot` for the answer. The window answers with `answer_agent`, keyed by
a number, because an event is one way and a window may be answering two
things at once.

The alternative was a mirror: every window pushing its buffer, its
annotations and its blocks into Rust whenever they settle, so the server
could answer from memory. That pays on every keystroke for a question
asked once a minute, and the Phase 2 gate measured flattening a megabyte
and sending it at 24 ms, so a ten megabyte document would be around a
quarter of a second of work per pause in typing. Asking costs nothing at
all until somebody asks.

What it costs instead is a timeout. Five seconds, which is an order of
magnitude over the slowest answer measured, and a window that has stopped
answering becomes a tool error a model can read rather than a call that
hangs. `Failed` is a separate answer from a timeout for the same reason:
a window that has since closed the tab knows something the server needs
to hear, and saying so beats waiting out five seconds to find out.

### Which window

The session's registry answers it, which is what design 6.5 already
keeps it for, and it is current within a tick of a tab opening. Two
things are then true and neither is free: the registry can be a tick
behind, and the window it names can have closed the tab since.

So a `Failed` from the window the registry named is not passed on as the
answer — it is about that window, and the question is about the document
— and neither is a registry miss the end of it. Both fall back to asking
the windows what they have open, which is a question about names and
sizes; asking each of them for the document instead would answer the
same thing by sending ten megabytes across the bridge to find out whose
it is.

## What it will not reach

Every tool is scoped to what the app has open: a document with a tab on
it, or, for a `write_document` that makes a new file, a path inside a
folder some window has open.

That is not the security boundary — the token is — and it does not need
to be. This is a socket on the loopback address and a secret in the
reader's own data directory, which is the same reach as anything else
they run. The scope is here because a markdown app's MCP server has no
business being a general file reader, and because a small surface is a
short argument.

## The token, the port, and the file

The port is the operating system's choice, because a fixed port is a port
something else may already have and losing that race would leave the app
with no server at all. The token is generated once and kept, because a
token that changed on every launch would break every client configured
with it. Both are written to `mcp.json` in the app's data directory, at
mode 0600, set again after the write: an atomic replace copies an
existing file's bits, and a file somebody widened should be narrowed
again rather than trusted.

Two checks run before a request reaches a tool.

**The token**, compared in constant time. The comparison is between a
string that arrived from the network and one that did not, which is
exactly the shape that leaks a secret a byte at a time to a caller who
can time it.

**The origin.** A page in a browser cannot read the token, but it can be
pointed at `127.0.0.1` — the DNS rebinding attack the MCP specification
tells local servers to guard against. A request carrying an `Origin` is
served only when the origin is this very port. A client that is not a
browser sends none and is unaffected.

Rotating a token replaces the file and leaves the server running on the
same port. Nothing a client was configured with changes, because the
configuration the palette hands out has neither the port nor the token in
it.

## `--mcp-stdio`

The same binary, in a mode that is neither the app nor a server: it reads
the endpoint file and forwards stdin to that port and the answers back to
stdout.

Reading the file every launch is the whole reason it exists rather than a
URL in somebody's configuration. The port changes on every launch and the
token does not, so a configuration with either in it would be either
wrong tomorrow or a secret in a dotfile. A configuration with neither is
right forever, which is what "Copy Agent Client Configuration" copies.

It forwards and does not interpret, with two exceptions, both headers the
transport needs and a client cannot know about: the session id the server
hands out at `initialize`, and the negotiated protocol version. Both are
set before anything reaches stdout, because a client that reads the
initialize response may send the next message immediately.

One direction only. The streamable HTTP transport also has a GET stream
for messages a server starts — sampling, elicitation, roots — and this
server starts none.

## A write

`write_document` is the one tool whose answer Rust holds itself, and it
does five things in order: write the file in its stored form, tell the watcher what
landed so it does not report the same change again anonymously half a
second later, take a snapshot authored `Agent` with the agent's name
beside it, emit the external change with that name on it, and record who
was here for the status bar.

It is asynchronous like the reads, and for one reason: whether a path is
one this server may write is the question of whether a window has it
open, so it goes through the same lookup, and "open" means the same
thing for a write as for a read. The cheap half of the scope — a path
inside a folder some window has open — is a string comparison and is
tried first.

The merge is then design 6.4's, unchanged: the reader's unsaved edits
survive, hunks both sides touched become a conflict widget, and the
gutter marks what moved. The only difference from a stray `echo >` is
that the app knows who did it, and that is the difference the whole of
design 9 is about.

Two small things follow from the name. `SnapshotInfo` gained an `agent`
column — migration 2, appended, because the history store outlives every
release — and the history panel shows that name instead of "Agent":
"just before the agent touched it" is a row a reader finds faster when it
says `claude`. And the shell does not take its own `external` snapshot
for a write that carries a name, because the write already took one and a
second row saying `Outside` about the same bytes would be a lie about how
many versions there are.

## The status bar

One cell: `Agent` when the server is up, `Agent · 2 connected` when
somebody is. Nothing at all when there is no server, which is a browser
build and a machine that could not bind the loopback address; an absent
thing should not take up a cell. Neither the port nor the token is in it
— one changes every launch and the other is a secret. Pressing it copies
the client configuration, which is the one thing a person wants from it.

The count is exact the moment a request has been served, because a
session begins and ends on one. It is late in exactly one case: a client
that goes away without a `DELETE` is counted until the transport's own
reaper closes it, five minutes of inactivity later. A minute's tick
recounts so that the bar catches up with the reaper rather than with the
next request.

## What was left

- **The reaper's five minutes.** A client that vanishes is still shown
  as connected until then. That number is `SessionConfig::keep_alive`'s
  and could be shortened, at the cost of closing sessions that were
  merely idle.
- **`changes_since` measures from the history, not from what was read.**
  The id `read_document` returns names the newest version the store
  holds, and the buffer may already be ahead of it — which is what
  `dirty` says on the same result. An agent that reads a dirty document
  and immediately asks what changed is told about the reader's unsaved
  edits. That is true, and it is not what the phrasing suggests.
- **No prompts, no sampling, no elicitation.** The server offers tools
  and resources. Nothing here needs to ask a model anything.
- **Windows is unverified, and the bridge is the part to doubt.** The
  release binary sets `windows_subsystem = "windows"`, so it is a GUI
  process with no console of its own. A client that spawns it with pipes
  for its standard handles should still work — the handles come from the
  parent, not from a console — but "should" is an argument and not a
  check, and if it does not, `--mcp-stdio` there needs a console binary
  of its own. No machine (ADR 0018, and the note that has stood since
  2026-09-08). Everything else in this package is platform-independent
  Rust and TypeScript; the endpoint file's owner-only mode is the other
  half that has no Windows implementation, and says so where it is
  written.
- **The endpoint file is not removed on quit.** A client then finds a
  port with nothing behind it, which the bridge reports in a sentence
  naming the app. Removing it would lose the token, which is the one
  thing that has to survive.
- **Nothing rate-limits a tool call.** An agent that asks a window for a
  ten megabyte document in a loop can make the window busy. The token
  holder is the reader's own agent, so this is a politeness problem
  rather than a security one, but it is unbounded.
