# ADR 0004: WP 0.4 the table widget

Status: accepted, 2026-09-07. Covers `packages/editor-core/src/preview/table`.

## Built in the plan's order

1. Read-only widget: a `Table` node whose block reveal range the selection
   does not touch is replaced, whole lines, by a block widget rendering a
   real `<table>`. Cells show their inline markdown through a small
   renderer (`inline-dom.ts`) that WP 1.4's Read renderer will absorb.
2. Editable cells: a click mounts one nested `EditorView` inside the cell
   whose document is exactly the cell's source. Its transactions are
   intercepted and rebased onto the outer document as one change shifted
   by the cell's start, with the same user event, so undo groups as usual.
3. Selection mapping: UTF-16 offsets plus the cell start, tested with
   escaped pipes and CJK.
4. Navigation: Tab, Shift-Tab, Enter, arrows; Tab in the last cell adds a
   row; Escape drops to source with the outer cursor at the cell offset;
   Mod-Z inside a cell undoes on the outer view and the cell resyncs.
   Arrow keys from the line next to a widget enter it, so keyboard users
   are not locked out.
5. Inline markdown in cells: rendered when not editing, source while
   editing.
6. IME: a synthesized composition sequence in the browser runner passes
   on Chromium and WebKit. The manual checklist on macOS and Windows with
   real input methods is not done; it needs a person at the keyboard and
   a Windows machine.
7. Structural commands: insert and delete row and column, format table
   with alignment and East Asian widths, materialize a missing cell. They
   are functions from state to change specs, tested in Node; only Tab's
   row insertion has a key.

## The nested editor applies first, the outer document is still the truth

The plan says the nested view is updated from the outer state, never the
other way round. The implementation applies the nested transaction to the
nested view first and then dispatches the rebased change on the outer
view. The reason is composition: an IME mutates the cell's DOM before any
event is cancelable, and CodeMirror's composition handling needs the view
that owns that DOM to apply the matching transaction synchronously. The
outer document keeps authority through a check that runs right after:
when the widget is rebuilt, the manager compares the cell's text in the
outer document with the nested document and overwrites the nested one if
they differ. A cell edit that another extension alters on the outer side
therefore lands as the outer side decided.

Two invariants make the rebasing exact: the nested document is the cell's
trimmed source and nothing else, and before rebasing the manager verifies
that the outer cell text equals the nested document the transaction
started from. If they differ, the edit is dropped and the nested view
resynced, rather than applied at a wrong offset.

Typed pipes become `\|` through a transaction filter on the nested view
so a literal pipe cannot split the cell; composition transactions are not
filtered. Newlines are refused, since a row is one line. A cell that the
source does not have, because a row is shorter than the header, is
materialized as ` |` before editing so the nested document has a range to
own.

## Where the active cell lives

`activeCellField` holds `{table, row, col, cursor}`; the table position is
mapped through changes. The outer selection stays outside the table while
a cell is edited, which is what keeps the table a widget under the reveal
rule. Any transaction that sets the outer selection on purpose closes the
cell, except undo and redo, which restore a selection as a side effect.
Event handlers on the widget never read positions from the widget
instance: a mapped widget can predate edits elsewhere, so the table
position comes from `posAtDOM` and the tree at click time, and the
manager reads the active cell from the state field at dispatch time.

## Focus and events

The widget returns true from `ignoreEvent`, so the outer view ignores
everything that happens inside a cell. CodeMirror also ignores selection
changes while its content element is not the active element, which is
the case while the nested view has focus. DOM mutations inside widgets
are ignored by the outer observer. No `contenteditable` fallback was
needed.

## Incremental widget field

The first version rebuilt every table widget on every transaction and
the 1 MB keystroke p95 in WebKit rose from 6 ms to 13 ms. The field now
maps existing widgets through the change and rebuilds only three sets:
the span of top-level blocks Lezer did not reuse, found by comparing old
and new tree children by object identity from both ends
(`changedRegion`); tables whose block reveal state flipped; and tables
that gained or lost the active cell. Lezer reparses a margin around a
change, so the region is a little wider than the edit, which is harmless.
With that, the numbers match WP 0.3:

| Size | Position | Chromium p50 / p95 / max | WebKit p50 / p95 / max |
|---|---|---|---|
| 1 MB | start | 5.1 / 6.4 / 10.8 | 4 / 6 / 8 |
| 1 MB | middle | 4 / 4.7 / 25.9 | 4 / 6 / 34 |
| 1 MB | end | 3.8 / 4.6 / 32.1 | 5 / 6 / 27 |

Math, Mermaid, image, and frontmatter widgets should join this field so
the document is walked once per change.

## Known limits

- A table inside a blockquote or list item loses its `>` or indentation
  visually while it is a widget, because a block replacement covers whole
  lines. The source is untouched.
- Rows with more cells than the header show only the header's columns,
  as GFM renders them; the extra text is still in the source and visible
  in Source mode or when the table is revealed.
- The manual IME checklist (design 7.5) on macOS and Windows is pending.
- Structural commands have no palette or keys yet beyond Tab.
