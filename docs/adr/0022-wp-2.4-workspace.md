# ADR 0022: WP 2.4 The folder workspace

Status: accepted, 2026-09-09. Covers folder open and the sidebar tree,
the watch on the folder, "New file" with inline rename, Cmd+P over the
folder, and Cmd+Shift+F content search (design 4.1, plan WP 2.4).

Scenario S6 is the whole of this work package: "The agent produced a
`research/` folder with twelve files. The human opens the folder. The
sidebar shows the tree, Cmd+P opens any file by fuzzy name, Cmd+Shift+F
searches contents, and each file opens in its own tab."

## One walker decides what the folder contains

The tree, Cmd+P and Cmd+Shift+F all ask the same question — is this file
part of the folder? — and they now all ask it of the same object: the
`ignore` crate's walker, which is ripgrep's. `crates/core/src/folder.rs`
builds it in one function and the search borrows it.

That is not only economy. Three answers to that question would have been
three ways to be wrong about it, and the reader would meet them one at a
time: a file in the tree that Cmd+P cannot find, a search result for a
file the tree does not show. What `.gitignore` names is left out of all
three or none.

`.gitignore` is honoured with `require_git(false)`, so a research folder
that is not a repository but has a `.gitignore` in it is still read the
way its author meant. Dotted names are left out as hidden, which is also
what keeps `.git` out of the walk.

## The walk behind Cmd+P is kept, and thrown away by the watch

Matching fifty thousand paths with `nucleo` takes a few milliseconds;
walking fifty thousand files takes hundreds. Cmd+P is typed into, so the
walk is done once and kept as a list of paths relative to the root.

Keeping it means it can go stale, and the answer to that is the same
watch the tree uses: when anything under the root is written, the index
is dropped rather than rebuilt, and the next query pays for one walk. A
checkout that rewrites a thousand files is one debounce, one drop and at
most one rebuild — and if nobody presses Cmd+P, no rebuild at all.

The walk is started on a thread of its own when the folder opens, so the
first Cmd+P usually finds it done. A query that arrives while it is
still walking waits on the same lock rather than starting a second walk.

## The watcher's events are filtered by hand

The walker reads nested `.gitignore` files as it goes. A watcher event
is one path with no walk behind it, so the folder watch carries its own
matcher built from the root's `.gitignore`, plus the dotted-name rule.
It is less than the walker knows, and it is what keeps a build writing
into `target/` from waking the tree several times a second.

The events also come back from wherever the folder really is: on macOS
every path through `/tmp` is a symlink into `/private/tmp`. The watch
resolves the root once and translates each event back into the path the
reader opened, because that is the path every row in the tree is built
from and the one they must be compared against.

## The tree is listings, not a shape

The sidebar holds one listing per folder it has read, keyed by path, and
derives its rows from them. That is the shape the watcher hands back —
"these folders may have changed" — so a refresh is reading those folders
again, and a folder nobody has expanded costs nothing.

Levels are read as they are opened. Twelve files are twelve rows; fifty
thousand files are still however many the reader has unfolded.

## The search streams, and the window names it

A search of a large folder has its first answers in milliseconds and its
last ones much later. Results are therefore events: Rust walks on a
thread, batches hits sixty-four at a time or every hundred milliseconds,
and the panel fills while the walk is still going.

The number identifying a search is chosen by the *window*, not by Rust.
Results are events and the call that starts a search is a round trip;
nothing orders the two, so a first batch can reach the webview before
`start_search` has returned. Had Rust named the search, the window would
have had to hold a batch it could not yet identify. Naming it in the
window removes the race rather than papering over it: every event
carries a number the window already knew.

A bad regular expression is compiled on the calling thread and comes
back as an error from the call itself, so a typo lands in the field it
was typed into instead of arriving later as a result that is not one.

## A result row shows part of a line, and says where the match really is

A matching line can be a whole minified file. The row shows the
neighbourhood of the match with an ellipsis at each end, which means the
offsets that highlight it are offsets into *that*, not into the line.

So a hit carries three numbers: `from` and `to` into the text shown, and
`column` into the line. The panel highlights with the first two and the
cursor goes by the third. One pair of numbers would have had to lie
about one of the two jobs.

Clicking a result puts the position on the *tab* rather than in a view:
files open in Read mode (design 4.2), which has no cursor. Both mounts
already honour a tab's scroll anchor, so the same two lines work in
either mode, and the selection is there for the reader who switches to
Edit.

## New file creates, then names, then opens

Design 4.5: "In the sidebar, 'New file' creates `Untitled.md` in the
selected folder and starts a rename." The file is made empty on disk at
once, and the numbering — `Untitled 2.md` when the name is taken — is
done in Rust, because that is where the folder is; a name chosen from a
listing the sidebar read a moment ago could be taken by the time it is
used.

It is not opened in a tab until the name is settled. Opening it would
have put the keyboard in the editor while the reader was still typing
the name in the sidebar, and which of the two focus calls won would have
depended on the order of two effects. Committing the name opens it,
which is also the better sentence: name the thing, then write in it.

A rename is refused when something of that name is already there. A tab
open on the file follows it through the same path the watcher's rename
takes, so the two cannot disagree.

## Recents are the same panel

Design 4.1 asks for "folder tree when a folder is open, recent files
otherwise". They are one panel, not two, because they answer the same
question — what can I open from here — and because a sidebar 220 pixels
wide has room for three tabs, not four.

The search field lives in that panel too, above the tree, and Cmd+Shift+F
opens the sidebar on it. Cmd+F is find in the document; Cmd+Shift+F is
the same gesture over the folder, and its results are a list of places
to go, which is what a sidebar is for.

## Cmd+P asks both sides

The tabs and the recents are still ranked in TypeScript, where they
already are: a handful of rows the reader most often wants, ranked
without a round trip. The folder is matched in Rust and appended, minus
anything already offered above.

Rust scores the whole relative path, so `adr conflict` finds
`docs/adr/0019-conflict.md`, and reports only the positions that fall
inside the file name, because that is what a row underlines. A folder
whose walk hit the two-hundred-thousand-file limit says so under the
results rather than quietly leaving files out.

## What was left

**One folder, one search, for the whole application.** Both live in
`Services`, not per window, and the result events go to every window.
There is one window today; WP 2.5 is where Rust starts keying this state
by window label, and where a second window can hold a second folder.

**The tree has no keyboard.** Rows are buttons, so Tab reaches them, but
there are no arrow keys, no type-ahead, and no way to rename without the
mouse. Cmd+P is the keyboard route to a file and it is the better one;
this is still a gap.

**Nothing is deleted or moved from the tree.** New file and rename are
what design 4.5 asks for. Deleting a file is not in this app yet, and a
drag between folders is not either.

**The search has no replace.** Find and replace across a folder is a
different promise from find: it writes to files that are not open, and
what it writes has no undo in this window. Design 4.5 asks for replace
in the document, which is what exists.
