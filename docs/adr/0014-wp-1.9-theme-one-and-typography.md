# ADR 0014: WP 1.9 Theme one and typography

Status: accepted, 2026-09-08. Covers theme one as data, the bundled
families, the type scale and the papers, the settings tab, zoom, and the
fence's language and copy button.

## The theme is a JSON file, and everything reads it

Before this package the app had three places that decided what a colour
was: `app.css` for the rendered page, `previewTheme` in `editor-core` for
the live preview, and Shiki's bundled `github-light` / `github-dark` for
fenced code. Two of them carried the same list of callout hues with a
comment saying WP 1.9 would merge them; the third disagreed with both
about what a keyword looks like.

`packages/theme/src/themes/one.json` is now the only place a colour is
written down. Everything else derives from it:

- `themeCss()` generates the stylesheet the window loads.
- `shikiTheme()` turns the code palette into a TextMate theme.
- `codeHighlight()` turns the same palette into CodeMirror `TagStyle`s.
- `tokens.ts` says, once, which TextMate scopes and which Lezer tags each
  of the sixteen token names answers to.

A theme is data and not code because Phase 2 adds three more of them, and
a reader's own is the obvious step after that. Nothing that consumes the
theme has to change for that to happen.

## The stylesheet is generated and checked in

`packages/theme/src/theme.css` is written by `theme.test.ts` through
`toMatchFileSnapshot`, which is how the read goldens work: the test fails
if the file has drifted from the JSON and `vitest -u` rewrites it, so the
diff in the pull request is the review.

Generated *and* checked in, rather than built at startup, because Rust
shows the window as soon as it is placed and before the first script
runs. A reader who chose dark should not be shown a white page first. The
same reasoning puts a `prefers-color-scheme` block in the generated file
for the instant before the settings arrive.

## Two attributes, and why the page and the window are separate questions

`applyAppearance` writes `data-appearance` and `data-paper` on the root
element and three lengths for the family, the size and the measure.
Everything else is already in the stylesheet.

The page's colours follow the paper, not the appearance. Design 11 makes
the page background a setting of its own — white, cream, yellow pad,
black — and calls black the high-contrast one. So black is a dark page
inside a light window: the chrome stays light, and the code on the page
takes the dark palette. One selector says so,
`:root[data-appearance="dark"], :root[data-paper="black"]`, and no third
attribute has to be kept in step.

That is also why the page has its own `--page-border`, `--page-muted`,
`--page-accent` and `--mark` rather than borrowing the toolbar's. A rule
that reached for the chrome's grey drew a pale line across the black
page, and `==marked==` text was pale yellow under pale ink. Both were
found by looking.

## The editor is told which paper it is on

`HighlightStyle` writes generated classes, so the code colours cannot go
through a CSS variable — they are two styles, and `themeType` lets
CodeMirror keep the one that matches. Which one that is comes from
`EditorView.darkTheme`, set through a compartment: `setDarkEffect` is
dispatched at every mount and whenever the settings change, because a
document state built under one paper may be shown on another.

## The golden, and what it found

`code-theme.browser.test.ts` renders the same fence twice — Shiki in Read
mode, CodeMirror in Source — and compares the colour of every character.
The golden file is the whole comparison, run-length encoded, so a change
to the theme is reviewed as a diff.

Two grammars will never agree about every character, and they do not:
whitespace joins whichever token the grammar felt like, and TextMate
gives leading indentation to the keyword that follows it. So the hard
assertion is over the characters that can be seen, and it holds. The
golden found two real faults on the way there: `special(string)` was
mapped to the escape colour, which painted every template literal
orange in Source and green in Read; and the bare `punctuation` scope was
winning over `comment` for the `//` that opens a line comment.

## Zoom is the reading size

Design 4.5 asks for Cmd+= and Cmd+-, and design 11 makes the size a
setting. Making them the same number means one thing to set, one thing to
remember, and a type scale that is only ever drawn at sizes it was drawn
for: the shortcuts step along `SIZES` and nowhere else. Cmd+0 is the
default. Rust puts a size that is not on the scale back onto it, so a
hand-edited settings file costs a rounding rather than an unreadable
window.

## Settings are a tab

There are no modals in this app (build plan rule 5), and a settings page
is a place the reader goes rather than something that happens to them: it
takes a tab, it can be pinned, and it comes back with the session.

The cost is that `Tab` needs a `kind`, and that everything acting on text
has to ask for `activeDoc` rather than `activeTab` — the shell now
distinguishes "there is a tab" from "there is a document", which it
should have done anyway. `TabState.kind` in Rust defaults to `document`,
so a session written before this package restores unchanged.

The page is dressed by the settings it is editing, so every choice
previews itself. Autosave is not on it: the design names it, but nothing
acts on it until WP 1.11, and a switch that does nothing is a lie.

## Fonts: Latin and Latin Extended only

Inter, Source Serif 4 and JetBrains Mono, all under the SIL Open Font
License, from the Fontsource variable packages. `fonts.css` declares
twelve faces by hand rather than importing the packages' own stylesheets,
which carry Cyrillic, Greek and Vietnamese as well: four megabytes of
installer for scripts this app has no typographic opinion about. Those
fall through to the system stacks each family is declared with, which is
what design 11 keeps fallbacks for. `THIRD-PARTY-NOTICES.md` records the
licences, and the settings tab names the three families.

## A Shiki defect, worked around

The first tokenization after a grammar is loaded sometimes carries the
first line's end state into the second, so a fence whose first line is a
comment comes out as a block of grey. It reproduces with Shiki's own
bundled themes, so it is not ours, and only ever affects the first call:
across two hundred samples no later call was wrong. `enhance.ts`
tokenizes the first block through a new grammar once and throws the
result away — one extra block per language per session.

## What this package does not do

- The other three themes of design 11, and per-document overrides. Both
  are Phase 2; the shape here is what makes them cheap.
- A language *name* for a fence. The label is the info string the file
  wrote, so there is no table to drift.
- The copy button in Edit mode. The fence there is a live editor, not a
  block of text to take away.
