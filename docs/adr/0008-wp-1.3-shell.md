# ADR 0008: WP 1.3 document store, tabs, modes, one window

Status: accepted, 2026-09-08. Covers `apps/desktop` after WP 1.3: the
document store, the command registry, the tab strip, the toolbar, the
palette, and the status bar.

## One EditorState per document, one mounted view

Design 6.5 asks for one document object per open path, shared by every tab
that shows it, and the plan asks that a second view forward transactions so
undo is shared. What the shell does instead is simpler and gives the same
guarantee: the document owns one `EditorState` — text, undo history, parse
tree, everything — and a tab owns only what is per view: mode, selection,
scroll. Only the tab in front has a mounted `EditorView`, so there is
nothing to forward. Undo is shared because there is one history, not
because two of them are kept in step.

Two consequences follow, and both are handled in `Workspace`:

- A tab that is not mounted still has a cursor, and edits made through
  another view move it. Every transaction maps the stored selection of the
  other tabs on the same document through its changes, the same way
  CodeMirror maps a live one.
- The mode is a compartment inside the shared state, so the mode of the tab
  coming to the front is reapplied when its view is mounted.

Split panes, where two views are visible at once, are not in Phase 1. When
they arrive they need the forwarding the plan describes; the seam is
`Workspace.mount`, which would become one call per pane.

## Dirty is a text comparison, not a buffer hash

The plan lists a buffer hash on the document. Hashing the buffer on every
keystroke costs more than the question it answers, so the document keeps
the `Text` it last saw on disk and `dirty` is `!state.doc.eq(base)`.
CodeMirror's `Text.eq` short-circuits on identity and compares by chunk, so
the common answer is cheap, and undoing back to the saved content returns
the document to clean, which a monotonic dirty flag would not.

The same `base` is the base snapshot for the three-way merge in WP 1.7, and
`reviewed` next to it is what the Changes badge will count from.

## Every command is registered once

`lib/commands.ts` holds a registry of `{ id, title, group, key, enabled,
run }`. The keymap, the palette, and the menu grouping are all derived from
it, so a new command is one entry and appears in all three (principle 6).
`lib/app-commands.ts` is that list for this app.

- Bindings are written platform independently (`Mod+Shift+P`), and `Mod` is
  Cmd on macOS and Ctrl elsewhere. Letters, digits, and brackets are matched
  by `KeyboardEvent.code`, so `Mod+Shift+[` still matches when the shifted
  character is `{`, and a non-US layout does not change what a shortcut means.
- The window's keydown handler ignores an event whose default was already
  prevented, which is how a key the editor handled — Enter, Tab, Backspace,
  undo — never reaches a command. Anything bound to a command belongs to the
  shell whether or not the command can run, so a disabled Save does not fall
  through to the webview's own Cmd+S.
- The nine tab jumps are registered `hidden`, bound but not listed, so they
  do not drown the palette.
- The menu bar is derived (`registry.menus()`) but not installed: a native
  menu is a Rust-side object and belongs with WP 1.8's window work. The
  grouping is what the palette shows today.

## No dialog asks about unsaved work

Rule 5 allows the two OS file panels and nothing else. Closing a tab with
unsaved changes therefore does not ask: the tab is closed, its document and
buffer are kept in the reopen stack, and the status bar says so. Cmd+Shift+T
brings the tab back where it was with its edits and its cursor. Autosave
(WP 1.11) will make this rarer still.

## What is deliberately not here

- **Read mode.** The switch shows three segments, and Read is disabled until
  the renderer lands in WP 1.4. `ViewMode` is `edit | source` until then, so
  the compiler points at every place that has to change.
- **The Changes badge.** The toolbar has its slot and renders nothing while
  the count is zero; WP 1.7 supplies the count.
- **Persistence.** Recents live in memory. Settings, the session file, and
  session restore are WP 1.8.
- **Autosave.** The status bar has the field and reports the save state;
  the 800 ms debounce is WP 1.11.
- **Cmd+N and the first-save panel** are here rather than in WP 1.11,
  because a shell that cannot make a document is hard to use by hand. The
  name proposed from the first heading stays in WP 1.11.

## Tests

`apps/desktop` gets two vitest projects. The framework-free half — key
parsing, the scorer, the registry, path and word-count helpers — runs in
Node. The half that needs runes and a real `EditorView` runs in the browser
project on Chromium and WebKit: `workspace.browser.test.ts` drives the store
against the fake IPC, and `shell.browser.test.ts` mounts the whole app and
uses it through the DOM — keys, clicks, the palette, drag and drop.

The plan asks for Playwright against the dev server. Vitest's browser mode
is Playwright, driving the same components over the same fake IPC, and it
shares the workspace's runner, reporters, and CI job; a second runner would
have bought only the dev server. The browser project lives in
`apps/desktop/vitest.browser.config.ts` because the Svelte plugin is a
dependency of the app, not of the workspace root.

## Performance

The shell does not touch the editing path, and the bench harness agrees.
On this machine, keystroke work at the 95th percentile: 100 KB documents
2.6 ms (Chromium) and 3 ms (WebKit); 1 MB documents 6.7 ms and 9 ms. First
paint of the mounted view stays under 35 ms. Full numbers in
`tools/bench/results`.

## The fuzzy scorer

A greedy subsequence match puts the wrong `p` first in
`markdown-app-build-plan.md`, so `lib/fuzzy.ts` runs a small dynamic program
instead: one row per query character, bonuses for a word start, a run, and a
match that ends a word, a small penalty for a gap and for a late start. It
returns the matched positions, which is also what the palette underlines.
