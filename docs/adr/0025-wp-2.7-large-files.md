# ADR 0025: WP 2.7 Large files and the window onto a document

Status: accepted, 2026-09-09. Design 8's two ceilings, and Read mode
rebuilt as a window onto the document rather than a rendering of it.

The plan's line is "above 10 MB Read mode only with a banner; above
100 MB refuse. Full virtualization of Read rendering on top of the
chunked renderer from WP 1.4. Measure the 10 MB bench file."

## Two ceilings, and one banner

`read_document` asks the file how big it is before it reads it. Over
100 MB it is refused with `TooLarge`, which carries the size and the
limit so the app can say what it found; the file is never pulled into
memory to be measured. Over 10 MB it opens, and its metadata says why it
cannot be edited.

That last part is the change worth naming. `DocumentMeta.read_only` was
a boolean meaning "not UTF-8". It is now a reason — `encoding` or `size`
— because the two read-only files are not read-only in the same way. A
file that is not UTF-8 can be opened in an editor and merely not saved;
one that is forty megabytes must not reach an editor at all, because
Read mode holds a screenful of it (below) while a live editor holds the
whole of it, with decorations over every visible line and an undo
history behind it. So `setMode`, the click that takes a reader from Read
into Edit, and the find bar all refuse for `size` and say why; the
compiler found every place that had been asking `read_only !== true`.

Both reasons get the banner design 8 asks for, over the page, in one
wording shared with the status line — and the encoding one carries the
offer to convert, which until now existed only as a palette command.

A document nothing can change gets no history. There is never a second
version to compare the first with, and a snapshot on open would send the
whole of a very large file over the IPC and into the store every time it
is opened.

## The page holds a window, not the document

WP 1.4 built the first screenful synchronously and the rest in idle
slices. Every block still ended up in the page: a megabyte was seven
thousand elements after a second of idle work, and ten megabytes would
have been seventy thousand blocks — hundreds of thousands of elements —
which is not a page a browser will lay out.

Read mode is now two passes that answer different questions.

The first walks the parse and writes down, for every top-level block,
where it begins and ends, what it will probably be worth in pixels, and
every id the page will have. It touches no DOM at all, so it runs over
ten megabytes in about three seconds of idle slices — and it is what
gives the outline every heading of a document the reader has seen one
screen of.

The second builds the blocks the reader can see, a viewport and eight
hundred pixels either side of it, and takes them out again when they
scroll away. What is not in the page is space: the article's own
padding, above and below, adding up to what those blocks would have
taken. Padding rather than spacer elements, so `.read` is still a list
of blocks and every rule written for it still means what it says —
including `.read > :first-child { margin-top: 0 }`, which is what makes
the arithmetic add up, since the space above a block already includes
the margin between it and the block before it.

Three hundred built blocks are kept out of the page after the reader
scrolls past them, so scrolling back is a re-insertion rather than a
render and a fence Shiki has already coloured stays coloured.

## Order-dependent facts are settled by the first pass

Building blocks in the order the reader reaches them is only sound
because nothing in a block depends on the ones before it. Two things
did.

Heading ids. Which of two headings called "Notes" is `#notes` and which
is `#notes-1` is decided by the order they are slugged in, and a block
built when the reader scrolls to it knows nothing about what came
before it. So the first pass owns every id: it renders each heading —
headings only, which is cheap — through a renderer of its own, in
document order, and a block built later takes those ids by the source
offset its headings carry.

Footnote numbers. `FootnoteNumbers` handed out 1, 2, 3 in the order the
render met each label, with a comment saying a chunked render and a
whole-document render therefore agree. They no longer do. So the
numbering is settled from the source instead: one pass records every
`[^label]` the text mentions, in order, and seeds the numbering before
anything is drawn. The back link goes to the reference the source makes
first, whichever one is built first, and a note nothing refers to is
still a note nothing refers to. Unseeded — a whole-document render, an
export, the goldens — the old behaviour is exactly what remains.

The third such fact was already handled: link reference definitions have
been scanned from the source since WP 1.4, for this reason.

## Heights, and the scrollbar's promise

A block that has never been on screen has no measured height, so the
first pass estimates one from the lines it spans and the measure the page
is set to, corrected by what blocks of that kind have actually measured
— a heading is a line and a half of a larger face with a blank line above
it, and no arithmetic here should have to know that. Every estimate is
replaced by a measurement the first time the block is drawn: the distance
to the next block, margins and all, which is exactly what the space
standing in for it has to be.

Measurement stops at the fold. Correcting a block above the top of the
viewport would move everything below it — the whole page — and the scroll
would have to be moved back by the same amount to hold the reader still.
That write is what turned out to break `Home` in a long document, because
WebKit animates a keyboard scroll and any write to `scrollTop` cancels
it. A block above the fold keeps its guess until the reader comes back to
it, and nothing has to be corrected for: the page under the reader is
made of blocks that have been measured, and what is above them does not
move.

The running totals live in a Fenwick tree (`heights.ts`). A plain array
of prefix sums answers both questions a scroll asks — where a block
starts, and which block is at a point — instantly, and costs a walk of
the whole document on every correction; at seventy thousand blocks, on
every frame of a scroll, that walk was the whole cost. One correction is
now seventeen steps instead of seventy thousand.

## What the numbers say

Bench, this machine, WebKit and Chromium (`tools/bench/results`):

| | first paint | walk to the end | scroll, median / worst | blocks in the page |
| --- | --- | --- | --- | --- |
| 100 KB | 13 / 15 ms | 55 / 99 ms | 1 / 3 ms | 42 |
| 1 MB | 20 / 28 ms | 233 / 502 ms | 1 / 3 ms | 42 |
| 10 MB | 43 / 72 ms | 2.8 / 4.1 s | 1 / 2 ms | 42 |

The 1 MB first paint was 17 / 25 ms before this work and its full render
1.16 / 1.20 s, leaving 7,333 blocks in the page. The ten megabyte file is
ten times the file the Phase 1 gate budgets at 100 ms and reaches first
paint in well under it, and a screenful of scrolling costs about a
thousandth of what a frame allows, at every size.

First paint got faster on the way. The renderer needed two whole-file
scans and the view wanted a third, and each of them cut the source into
a quarter of a million strings to find that almost none of them held
anything. They are one walk now (`scanSource`), over line *ranges*, and
a line is only cut out of the source when a cheap test says it might
matter — 30 ms of a ten megabyte open became 12.

The walk to the end was sixteen seconds before the parse step was
raised: an idle callback runs about once a frame, so twenty kilobytes
per slice is a minute of doing very little on a large file. The first
call still asks for a screenful at a time, because that one is the
reader waiting.

## What the twelve megabyte file found

Five defects, all of them in the by-hand pass and none of them in the
tests, which is what the pass is for.

**A hidden block has no box.** A comment is in the page and folded away
(design 4.3), so its `offsetTop` is zero — and measuring the block above
it against that put one block of a four hundred kilobyte document at
minus a hundred thousand pixels and the next at plus a hundred thousand,
which the calibration then spread over every block of that kind. The
document ended up on a scrollbar of thirty-three million pixels, which
is the largest a browser will draw. Blocks with no box are now worth
nothing and nothing is measured from them, no measurement that is not a
positive distance is recorded at all, and no height can be negative.

**The panel that looked empty.** The outline is a flex column, and a
flex column shrinks its children to fit rather than letting them
overflow. At a hundred headings that is a pixel off each; at the ten
thousand of this file it is rows six pixels tall in a panel that reads
as empty. The three scrolling panels — outline, folder tree, history —
now say their rows do not shrink.

**Home did not go home.** WebKit animates a keyboard scroll, and any
write to `scrollTop` stops it. The measurement pass wrote one on nearly
every frame, so `Home` in the long document stopped wherever the first
correction landed — section 4,580 of 10,919, then 700 on the next press.
This is what moved measurement to the fold and down: a block above the
fold is not corrected, so there is nothing to correct the scroll for,
and the animation runs to the top.

**Unfolding brought nothing back.** A fold takes blocks out of the
middle of the run and the window is filled from its ends, so the blocks
came out and never went back in. A fold change now empties the page and
builds the window again, which costs no rendering because the blocks are
all still in hand.

**The estimates were half a heading short.** A heading is a line and a
half of a larger face with a blank line above it, and guessing it as a
line of body text left the document six percent shorter than it is —
enough that `End` landed at 43 percent of the way down and needed six
more presses. Guesses are now corrected by what blocks of that kind have
actually measured, which needs no table of what the stylesheet says: one
press of `End` now reaches 98 percent, and the rest converges as those
blocks are measured.

## What was left

- Find has no Read mode of its own, so `Cmd+F` in a document too large
  to edit says so instead of opening a bar that would report no matches
  in a document full of them.
- A selection is lost if the reader scrolls far enough that the block
  holding it leaves the page. Selecting text and then scrolling two
  screens away before annotating it is not a flow anyone has; the fix,
  if it ever matters, is to hold the blocks a selection spans.
- The estimates are made from the lines a block spans and the average
  width of a character, so a document of tables and images has a
  scrollbar that is honest about where things are and approximate about
  how much is left, until the reader has been there.
- The outline of a very large document arrives over the first few
  seconds, as it did before. Nothing says so in the panel beyond the
  entries appearing.
- A ten megabyte file still holds ten megabytes of text, a parse tree,
  and a slot per block in memory. The ceiling that matters for memory
  is design 8's hundred megabytes, and nothing measures it yet.
- `End` lands close to the end rather than at it, because the blocks it
  scrolls past are still guesses when the scroll is aimed. Each press
  measures more of them and gets closer; the outline, and any anchor,
  goes exactly where it says.
- The outline panel builds a row per heading, which is ten thousand
  buttons for this file. It is the page that holds a window; the panel
  beside it still holds everything.
