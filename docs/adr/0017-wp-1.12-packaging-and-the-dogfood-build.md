# 0017 — WP 1.12: packaging and the dogfood build

Date: 2026-09-09. Status: accepted, with two parts blocked on accounts
that do not exist yet (see "What is not done").

## Context

Phase 1's last package turns a repository into something that can be
installed on a machine that did not build it, and updated afterwards. The
plan asks for four things: signed and notarized macOS and Windows
bundles produced in CI, `.dmg` and `.msi` installers, an updater with a
static release manifest, and no telemetry or crash reporting.

Two of those need credentials with weeks of lead time, and the plan says
so — Apple Developer Program enrollment was meant to happen in Phase 0.
It has not. So this package is written to be complete in the parts that
do not need an account, and to fail loudly and legibly in the parts that
do.

## Decisions

### The updater is the smallest one that can carry a fix

The design does not mention updates at all; the plan adds them for one
reason, which is that a build being dogfooded has to be able to receive a
fix. So there is no update channel, no settings, no "remind me later",
and nothing that installs itself.

The rule that shapes it: **an update the reader did not ask about is
never allowed to interrupt.** An automatic check that finds nothing, or
that cannot reach the network at all, says nothing whatsoever —
`describeUpdate` returns the empty string for `none` and for `failed`,
and the status bar has no cell. Only `checkForUpdates(true)`, which is
the palette command and the Settings button, reports back either way.
That is the whole difference between the two paths, and it is what the
tests in `update.test.ts` are mostly about.

There are no dialogs, per the build plan's rule 5. An available update is
one cell at the end of the status bar which says what it is and does it
when pressed: press once to download, press again to restart.

### The restart flushes first

`restartForUpdate` calls `flushPending()` before it relaunches. A
relaunch is a close the window is never told about, so an autosave still
sitting on its 800 ms timer would go out with the process — and the
reader would rightly blame the update for the lost sentence. The browser
test for it fails with `expected '# One\n' to be '# One\nedited\n'` when
the flush is removed, which is what makes it a test rather than a
comment.

### The manifest is built from the signatures, not from a list of names

`tools/release/manifest.mjs` reads each platform's artifact directory,
finds the one `.sig` file in it, and takes the artifact as the file that
signature is named after. Nothing anywhere maintains a list of expected
bundle names, so the manifest cannot quietly disagree with what was
actually built.

Two `.sig` files in one directory is an error rather than a choice. A
Windows job that produced both an `.msi` and an NSIS `.exe` can only
serve one of them as *the* update for that platform, and picking one
silently is how the wrong installer ships to everybody.

### One version in three files, with a test

The Cargo workspace, `tauri.conf.json` and the desktop `package.json`
each carry the version. The config's copy is the one the updater compares
against the manifest, so if it drifts from the tag the release either
never offers itself or offers itself forever. `pnpm release:version`
writes all three and a test asserts they agree, which turns a silent
release-day failure into a red test.

### The release is drafted, never published

`release.yml` ends at a draft. Publishing it is the moment
`releases/latest/download/latest.json` starts resolving and every running
copy is offered the update — so that moment is a person's decision, taken
after opening the `.dmg` on a machine that did not build it. That check
is the only one that catches a signing or notarization failure, because
the machine that built the app trusts it either way.

### No entitlements file

Tauri enables the hardened runtime by default when it signs, which is all
notarization requires. The app is not sandboxed, so it needs no
entitlement for the network or for the files the reader opens, and
WKWebView runs its JavaScript in a system process with its own. An
entitlements plist here would grant nothing and claim to be doing
something.

### The notices ship inside the bundle

`THIRD-PARTY-NOTICES.md` said this package was where it had to reach the
application rather than only the repository. It is now a bundle resource
— verified in the built `.app` at
`Contents/Resources/THIRD-PARTY-NOTICES.md` — and the Settings colophon
says so.

### No telemetry, no crash reporting

As the plan's section 12 says. Nothing was added. The OS's own crash
reporter is what there is.

## What is not done, and why

**macOS signing and notarization have never run.** The workflow imports a
Developer ID certificate into a throwaway keychain, passes the App Store
Connect key to Tauri's notarizer, and staples — but there is no Apple
Developer Program enrollment behind it, so none of that has been
exercised. Without the certificate the workflow emits a warning and
produces an unsigned bundle rather than failing. **Enrollment is now the
critical path for Phase 1**: it costs $99, takes days to weeks, and
nothing downstream can be tested until it is done.

**Windows signing is deliberately absent from the workflow.** Azure
Trusted Signing is configured through a `signCommand` naming an endpoint,
an account and a certificate profile; none of those three can be guessed,
and config that has never run is worse than an honest gap. `docs/release.md`
section 5 has the exact overlay to add. Windows builds unsigned for now.

**Nothing has been released.** There is no git remote. The endpoint in
the config is the one the bundle identifier implies,
`github.com/victor-eu/md-reader`; it is baked into every build, so it has
to be right before the first published release, not after.

**There is no LICENSE file.** WP 0.1 said the repository licence had to
exist before the first corpus file was committed, and it does not. It is
not a decision this package can make.

## Consequences

- The private updater key lives at `~/.config/mdreader/updater.key`,
  outside the repository. Losing it means no installed copy can ever be
  updated again — the pubkey is compiled into every build, and a new one
  would be rejected by every copy already out there.
- The nightly CI bundle now builds with `src-tauri/unsigned.conf.json`
  merged in, which turns updater artifacts off. Without it every nightly
  would fail for want of a signing key that workflow has no business
  holding.
- `Help` joins File, Edit, View and Go as a menu group.
