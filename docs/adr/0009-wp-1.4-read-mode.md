# ADR 0009: WP 1.4 Read mode renderer and click-to-edit

Status: accepted, 2026-09-08. Covers the read renderer in
`packages/markdown/src/render`, the mounted view in
`apps/desktop/src/lib/read`, the sidebar with the outline, and the three
libraries Read mode hands work to.

## One renderer, two adapters

The renderer walks the Lezer tree and produces a small node tree —
elements with a tag, attributes, a source range and children, and text runs
with a source range — which two adapters consume: one builds DOM, one
writes an HTML string. Read mode mounts the first; the goldens and the
HTML export of WP 3.2 use the second.

The alternative, a renderer that writes DOM directly and a separate one
that writes HTML, would have to be kept in step by hand and by review. Here
the two adapters are forty lines each over one walk, so the document they
produce is the same document by construction. The browser goldens assert
exactly that: they mount the nodes through the DOM adapter, read the
mounted tree back, and write it with the same writer the Node goldens use.

Every element carries `data-from` and `data-to`, as design 6.2 requires.
Text runs carry their range too, and a flag saying whether the run is a
verbatim slice of the source; escapes and entities are the only runs that
are not, because they render one character for several.

## Read mode renders the editor's parse, not a second one

Design 4.2 says Read mode is not a separate parser, and the obvious reading
of that is "call the same parser twice". What the view does instead is ask
the document's `EditorState` for its syntax tree through
`ensureSyntaxTree`, which is the same incremental parse the editor uses,
cached in the state's language field. Switching from Edit to Read costs no
parsing at all when the editor has already parsed the document, and the two
modes cannot disagree about what the document is, because there is one
tree.

It also solves the first-paint problem for free. `ensureSyntaxTree(state,
upto, timeout)` parses up to an offset with a time budget and keeps its
progress, so the view can ask for the first few thousand characters,
render them, and ask for more when the browser is idle.

## Chunked rendering, and what "first paint" means

The view parses and renders the first screenful synchronously in its
constructor and the rest in idle slices. A slice parses up to 20 KB
further, renders the whole blocks the tree now covers, and stops when its
time budget runs out; the first pass stops as soon as the rendered height
covers the viewport plus a margin. A block whose end is at the end of a
partial tree is left for the next slice, because it may still grow.

`requestIdleCallback` is Chromium-only among the engines that matter, so
the view falls back to a short timeout. WebKit is the engine on macOS, so
this is the path that runs on the developer's own machine, not the
fallback.

Two consequences worth naming:

- The reference definitions a `[label][ref]` link needs are scanned from
  the source with a regular expression rather than read out of the tree,
  because a chunk must render the same way whether the definition is above
  it or below it. The scan skips fenced code, which is where a line that
  only looks like a definition is most likely to be.
- Heading ids are assigned as the renderer meets headings, so they depend
  on document order, not on how much has been rendered. The outline walks
  the same headings in the same order through the same renderer, so the
  ids in the sidebar and the ids in the page cannot drift.

## Click-to-edit resolves through the text runs, not through the blocks

The DOM adapter records, in a `WeakMap` keyed by text node, where each
verbatim run starts in the source. A click asks the engine for the caret
under the pointer and adds the offset inside that text node to the run's
start, so the cursor lands on the character under the pointer rather than
at the start of a paragraph. The alternative — wrapping every run in a
`<span data-from>` — would have put a second element around every word of
every document and made the goldens unreadable.

Two fallbacks sit behind it. A subtree whose text another renderer rewrote
— a highlighted code block — is marked `data-verbatim`, and a click inside
it counts the text before the clicked node. Anything else resolves to the
`data-from` of the nearest enclosing element, which is a block start.

`caretPositionFromPoint` and `caretRangeFromPoint` are both used, in that
order; between them every engine we support answers.

## Folding, and where the fold state lives

A fold hides the top-level blocks that follow a heading, down to the next
heading of the same level or higher. The view keeps the blocks in an array
and replays a stack of folded levels over it, which handles nesting and
costs nothing to extend when a new chunk arrives. Headings nested inside a
blockquote or a list item are in the outline but do not fold; folding a
section of a quotation is not a thing readers ask for.

The folded ids live on the tab, not in the view, so they survive a mode
switch and a tab switch. Whether they survive a restart is WP 1.8's
question, and the answer will be "yes" because the tab is what gets
serialized.

## A mode switch keeps a source offset, not a scroll position

The two views measure in different units — one in rendered pixels, one in
editor lines — so a scroll position means nothing across the boundary. When
either view is unmounted it writes an anchor onto the tab: the source
offset at the top of its viewport. The other view scrolls that offset to
the top when it mounts. A click-to-edit sets the anchor to the clicked
offset and the y where it was clicked, so the paragraph the reader clicked
stays where their eye already is.

## Shiki, KaTeX, and Mermaid: after paint, on demand

All three are dynamically imported and run per chunk after it is in the
page, so a document with no code, no math and no diagram never loads them,
and a slow diagram never delays the text. Every element is marked when it
is done, so re-running over a chunk is free.

- **Shiki** uses the JavaScript regex engine, not the WebAssembly one. A
  webview under `default-src 'self'` cannot compile WebAssembly without
  `wasm-unsafe-eval` in the policy, and widening the policy of the app for
  syntax colours is the wrong trade. Both themes are loaded and emitted as
  CSS variables, so the page follows the system without highlighting twice;
  WP 1.9 replaces the pair with the shared token theme.
- **The language set is curated**, thirty-six grammars and their aliases.
  Shiki's own bundle is two hundred, and naming it puts fourteen megabytes
  of TextMate JSON in the installer for languages nobody writes markdown
  about. An unlisted language renders as plain code. Adding one is a line
  in `LANGUAGES`.
- **KaTeX** renders with `trust: false`, as design 6.2 says. The TeX source
  stays on the element in `data-tex`, so the source is still there when
  the reader switches to Edit.
- **Mermaid** renders with `securityLevel: 'strict'` into the element that
  held the fence. A diagram that fails to parse keeps its source and says
  why in a tooltip, rather than disappearing.

## Links leave through the opener, or not at all

An absolute `http`, `https`, `mailto` or `tel` link opens in the system
browser through `tauri-plugin-opener`; the capability is narrowed to
`allow-open-url` plus the plugin's default URL scope, so the app cannot be
talked into opening a file path. A `#` link scrolls to the heading with
that id, rendering more of the document first if it has not got there yet.
A relative link says in the status bar that it needs the folder workspace,
which is WP 2.4. The webview itself never navigates.

`javascript:` and every other scheme is dropped at render time: the link
becomes its own text.

## What is deliberately absent

- **The inline HTML whitelist** of design 5.2. Until WP 1.5 an HTML block
  or tag renders as the literal text it is, which is safe by default and
  honest about what the file says. That includes the `<span style="color">`
  of design 4.3: colours arrive with the annotation work in WP 1.6.
- **Images.** A remote or `data:` image renders; a relative one shows its
  alt text, because loading it needs the asset protocol and the
  per-document scope of WP 1.5. A broken-image icon would have looked like
  a bug.
- **The frontmatter widget.** Frontmatter renders as the YAML it is.
- **The comment toggle.** Comments are folded away, as design 4.3 says,
  and the element is in the page with `hidden` so WP 1.6 has something to
  show. Text after a `-->` on the same line stays visible, because it is
  visible in every other renderer too.
- **Virtualization.** Read mode builds the whole document, in chunks. The
  10 MB case and the banner are WP 2.7; the chunked renderer is what that
  work will virtualize.
- **Footnotes**, which the dialect does not parse yet (WP 1.5).

## Tests

- Node, over fixtures: the tree walk for every construct, ranges, escaping,
  the slugger, the reference scanner, and the outline.
- Node, over the corpus (270 files): nothing throws, every range is inside
  its parent and inside the document, every verbatim run is the source it
  claims, every construct the parser found is in the output, and no mark
  that was consumed shows up inside the element it produced.
- Node and both browsers, over the golden set: 137 files — every
  adversarial file and a fixed sample of a hundred generated ones — with
  one golden file each rather than one per engine. The renderer is ours and
  builds the same nodes everywhere, so a difference between Chromium and
  WebKit would be a bug rather than a second expected output, and the
  browser test asserts that by comparing both engines against the same
  file. `vitest -u` rewrites them and the diff is the review.
- Both browsers: click every word of a fixture and check the offset lands
  inside that word; the three enhancers against the real libraries,
  including that Shiki does not change a character of the code and that a
  click inside a highlighted block still resolves; Read mode through the
  workspace — outline, folding, click-to-edit, the anchor across a mode
  switch, and a long document arriving in chunks.

## Performance

The Phase 1 gate budgets open to first paint at 100 ms for 1 MB. On the
bench runner, with the document already in memory, building the editor
state, parsing as far as the viewport needs, rendering those blocks and
forcing layout:

| Document | Chromium | WebKit |
|---|---|---|
| 100 KB first paint | 7.7 ms | 8 ms |
| 1 MB first paint | 9.3 ms | 10 ms |
| 1 MB rendered whole | 625 ms | 710 ms |

First paint is flat in document size, which is the point of the chunking:
what it costs is one viewport. The whole-document number is the idle work
that follows, and it is recorded because a renderer that took a minute to
finish a long document would be a problem this budget alone would not
show. The numbers that matter for the gate come from WKWebView and WebView2
on the pinned machines; these are the regression guard.

Keystroke latency is unchanged: this work adds nothing to the editor.
