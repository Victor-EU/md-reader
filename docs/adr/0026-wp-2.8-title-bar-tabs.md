# ADR 0026: WP 2.8 Tabs in the title bar

Status: accepted, 2026-09-09. The strip is the window's title bar on
macOS, and the window's own three buttons sit in it.

The plan's line is "the Chrome look. macOS: overlay title bar with the
traffic lights inset beside the tabs. Windows: no native decorations,
custom caption buttons, drag regions, and the Windows 11 snap layout
flyout on the maximize button, which needs the native hit test.
Double-click to maximize, mixed-DPI moves, and full screen verified on
both."

The Windows half is not done and is not attempted: there is no Windows
machine to check it on (ADR 0018, and the same note that has stood since
2026-09-08). On Windows and Linux the window keeps its own decorations
and the strip sits under them, which is what Phase 1 shipped.

## The window gives its bar up

Two lines of `tauri.conf.json`: `titleBarStyle: "Overlay"`, which makes
the title bar transparent and lets the webview fill the window behind
it, and `hiddenTitle: true`, because a title drawn across the middle of
the tab strip is the one thing that would give the trick away. The
configuration is also what `spawn` copies for every window after the
first, so a torn-off tab (WP 2.5) comes up in a window dressed the same
way without another line.

## Who places the three buttons

Tauri has a `trafficLightPosition`, and this work package used it first.
It does not do what it looks like it does, and both halves of that are
worth writing down.

The horizontal half works: it sets each button's `origin.x`, and wry
re-applies it whenever the view under the buttons draws, which is what
survives a resize. The vertical half does not. It sets the height of the
title bar's container view and leaves the buttons' own `y` alone, in the
hope that AppKit will re-centre them in the new height. On macOS 15 it
does not — the button keeps its eight-point margin from the top of the
container whatever the container's height is — so the number has no
visible effect at all. Worse, the position is applied when the window is
built and then undone by the layout that showing and placing the window
provokes, and only re-applied the next time that view draws: the buttons
came up at the system's own place and *jumped* to ours on the first
resize.

So the buttons are left where macOS puts them, and the strip is sized to
them instead. They are twelve points tall, eight points down from the
top of the window, which makes 28px the one strip height that leaves
them centred in it — and 28px is a comfortable tab. `padding-left: 72px`
is the room kept clear beside them: the third button ends sixty points
in, and the twelve after it are the gap before the first tab.

That is one hardcoded number about somebody else's furniture, and it is
the honest trade. The alternative was to own the buttons — to move them
ourselves, on every event that AppKit re-lays the title bar out on — for
a strip a few pixels taller. The system's own placement cannot drift out
of step with the system.

Full screen is the one time the room is wrong: macOS takes the buttons
back and draws them over the top of the screen itself, and the strip
should run to the window's edge. The only news of it the page gets is
the window changing size, and asking the OS at that moment turns out
not to be enough. Entering full screen is flagged before the window
resizes; leaving it is flagged at the end of the animation that follows
the last resize the page hears about, so the one question asked then
still comes back `true` — which is exactly what the by-hand pass found:
after leaving full screen the tabs sat under the buttons until the
window was next resized.

So `watchFullScreen` asks once the window has stopped changing size, and
three more times over the following second while the animation finishes.
A resize restarts that run rather than adding to it, so dragging an edge
asks once, at the end.

## Everything that is not a tab is the window

`data-tauri-drag-region` on the strip and on the space after the last
tab. Tauri reads it: a press moves the window, a double-click zooms it,
and on macOS the zoom waits for the mouse to come up and is cancelled if
it moved, which is what the system does. None of that is ours to write.

Bare rather than `deep`, deliberately. Tauri's rule for a bare region is
that only a press landing on the marked element itself counts, so a
press on a tab, on its close button, or on the new-tab button is that
control's; the strip's own background, the corner kept for the buttons,
and the gap after the last tab are the window's. It also means the
existing drag on a tab — reorder, or tear it into a window of its own —
is untouched.

Two permissions had to be added to the capability:
`core:window:allow-start-dragging`, because `core:window:default` grants
`internal_toggle_maximize` but not the drag, and
`core:window:allow-set-title` for the naming below.

## The front of the window

The Chrome look is one relationship: the tab you are in is the same
surface as the bar under it, and the strip behind them is not. The
palette already had the colour for it. `ui.active` is documented as the
front of the page and was the active tab's; the toolbar now takes it
too, and the tab loses its bottom edge, so the two read as one surface
with the tab's shoulders rounded off it. The quiet tabs are the strip's
own colour with a hairline between neighbours, which goes the moment
either of the pair comes forward — hover included, which is why the rule
needs no `:has`.

`active` is lighter than `bg` in all eight palettes, light and dark, so
the relationship holds everywhere without a second set of colours. What
did have to follow is the contrast floor: the chrome's text is now drawn
on `active` as well as on `bg`, and `theme.test.ts` holds both. The
worst case across the eight is 5.2 on muted text, against a floor of
4.5.

The accent stripe along the top of the active tab is gone. It was a
useful signal when the strip was a row inside the window; at the very
top edge of the window it is a line across the top of the screen, and
the shape and the colour are the signal now.

## A tab gives way before the strip does

Tabs were capped at 220px and the strip scrolled when they did not fit.
They now shrink to a 96px floor first — enough for a few letters and the
close button — and only past that does the strip scroll, with the active
tab kept in view as before. That is what a browser does, and it is the
difference between nine tabs you can read and nine tabs you have to
scroll through.

Which turned up the second thing the by-hand pass found. The active tab
was brought into view when it changed, and only then; the strip getting
narrower under a scrolled run of tabs pushes the one the reader is in
off the end of it without any tab having changed. A `ResizeObserver` on
the strip is the second reason to bring it back.

The strip also gained the one control it did not have: a `+` after the
last tab, running the same command as Cmd+N and named after it.

## The window still has a name

Nothing draws it any more, but macOS lists windows by it in the Window
menu and under Mission Control, and with more than one window open (WP
2.5) every one of them answering to "MD Reader" is no help. The window
is named after the tab in front, from the same disambiguated labels the
strip draws, and falls back to the app's name when there is no tab.

## What was left

- **The Windows half of the package.** No machine. Custom decorations,
  caption buttons, the snap-layout hit test: none of it is written.
- **Mixed-DPI moves are unverified.** This machine has one display. The
  buttons are the system's and are laid out in points, and the strip is
  laid out in CSS pixels, so there is nothing in this work package that
  holds a device pixel — but that is an argument, not a check.
- **The gutter is a constant.** 72px assumes three twelve-point buttons
  twenty points apart. If macOS changes that, the gap changes with it,
  and nothing here would notice.
- **Dragging a tab in an unfocused window** first focuses it, as
  everything in an unfocused window does. Chrome accepts the first click
  on its strip; doing the same means `acceptFirstMouse` on the whole
  webview, which would also put a caret in the editor on the click that
  brings the window forward.
- **Tab reorder by drag could not be driven by hand.** A synthesized
  drag reaches `dragstart` and `dragend` but never delivers `drop`, so
  it always reads as a tear-off. The reorder has a browser test; the
  same limitation was recorded in WP 1.3.
- **No tab tearing preview.** WP 2.5 left it here, and it is still
  whatever WebKit draws for a dragged element.
- **A pinned tab is still a narrow tab**, not the icon Chrome shrinks it
  to. There is no favicon to shrink it to.
