# ADR 0023: WP 2.5 More than one window, and tearing tabs between them

Status: accepted, 2026-09-09. Covers second windows, moving a tab from
one to another, tearing one out into a window of its own, the state each
window keeps for itself in Rust, and what a launch puts back (design 4.1,
6.5, plan WP 2.5).

Design 6.5 sets the rule this work package is built on: "Because each
window is its own webview, a second view lives in the same window as the
first; moving a document to another window moves it, with its view state
and undo history, rather than sharing it."

## A document belongs to one window

Two webviews share nothing. A document is an `EditorState` — the buffer,
its undo history and its parse tree — and there is no way to put one in
two webviews and keep them the same document. So the app does not try:
one document is open in one window, and the ways it could have been
opened twice are all closed.

`reveal_path` is what closes them. Every way the reader opens a file —
the open panel, the palette, a click in the tree — asks Rust first
whether another window has it, and if one does, that window comes
forward with the file in front instead of a second copy opening here.
The registry that answers is the session, the same one that routes a file
the OS hands us (WP 1.8): no second bookkeeping to keep in step.

That leaves a document with two views in one window, which WP 1.3 already
allows and which the design keeps. A tab whose document has a second view
here is refused a move, and says why. Moving one of the two would put the
document in two windows through the back door; moving both would be a
gesture on one tab doing something to another.

## The tab is carried, not the file

What crosses is everything the window taking it in needs to be where the
other one was: the buffer, what the file held when that window last saw
it, what the reader had already looked at, the view state, and the
editor's own serialization of its undo history. Rust carries the last of
those without reading it — `EditorState.toJSON` with `historyField`, a
string only a window of the same build can make sense of.

Reading the file again instead would have been smaller, and wrong: a
document moved with unsaved changes in it would arrive as the file on
disk, and the reader's work would be in neither window. Carrying the base
and the reviewed text with it is what makes the dirty dot and the Changes
badge mean the same thing on the other side, and what lets this window
work out for itself what has changed since the reader last looked.

The buffer travels twice: in the clear, and inside the serialized state.
That is deliberate. It costs a copy of a string on a gesture nobody makes
twice a minute, and it turns a payload the editor cannot parse into a
document that has lost its undo history rather than a document that is
lost.

## The move fails safely

The tab leaves this window only after the other one has been given it.
`move_tab` answers with where it went; a window that cannot be reached is
an error, and the tab stays where it is, with its watch put back.

Rust keys a file watch by path, one entry per path, so the two windows
cannot both hold one. The window giving the tab up drops the watch before
it asks — the other order leaves the file watched by nobody, which is the
failure you do not see until an agent writes the file and nothing says
so.

A window made for a torn-off tab is not listening yet, which is the same
problem a file argument has at launch and gets the same answer: the tab
waits in a queue, and the window drains it when it boots. Draining is
also how it says it is listening, so nothing is delivered twice.

## The pointer is read in Rust, not in the webview

The gesture design 4.1 asks for is dragging a tab out of the window. A
drag that has left the window is past what the page can measure: what
WebKit reports as the end of one is *near* where the reader let go.
Measured in the real app, the point in a `dragend` was out by (47, 16)
one time and (70, -20) the next, which is the difference between a tab
landing in the window under it and a tab tearing off beside it.

So the webview says only that the tab was dropped, and Rust reads the
pointer itself. The window manager knows where the pointer is, in the
same units a window frame is in, on whichever monitor it is over — no
CSS pixels, no scale factor, nothing to convert. A window under that
point takes the tab in; nothing under it tears the tab into a new window
whose corner goes exactly there. The command in the palette passes no
drop at all, and cascades over the window the tab came from.

Escape during a drag is the one thing the page still has to say: the
browser reports a cancelled drag exactly as it reports a tab dropped on
the desktop, so the key press is what tells them apart.

## An event addressed to one window was reaching all of them

Rust has always sent some events to one window — the file a launch is
opening, the request to write down what a window holds before it closes.
With one window it was impossible to tell that they were arriving
everywhere.

They were. A listener registered with `listen(name, cb)` asks for events
to *any* target, and Tauri delivers every emit to those, addressed or
not. With a second window open, that is the app closing every window
because one of them was asked to close, and every window adopting a tab
torn off in one of them. The window now listens as itself —
`events.x(getCurrentWindow()).listen(...)` — and an addressed event goes
where it is addressed. Events sent to everybody still arrive.

This was found by reading Tauri's event matching while writing the tab
handoff, and the by-hand pass confirms the fix: closing one of five
windows closes one of five windows.

## What each window keeps for itself

The folder, the tree behind it, the Cmd+P index and the content search
are per window now, keyed by label in `Services`. Two windows are two
workspaces: a reader can have the repository in one and the notes folder
in another, and the tree in one says nothing about the other. The watch
events and the search results are addressed to the window whose folder
they belong to.

The watcher on open documents stays one, app-wide, and its reports go to
every window. That is not an oversight: a document belongs to one window,
so exactly one window has anything to do with a given path, and the
others drop the report by asking whether they hold it. Addressing it
would mean Rust keeping a second registry of who holds what, current to
the millisecond, to save each window one comparison.

## What a launch puts back, and what it does not

The session has always been a list of windows keyed by label; now more
than one of them is real. A launch opens every window the session
records, each with its own frame, its own tabs and its own folder. The
configuration always opens `main`, so a session whose windows were all
made later takes that window over for its first entry rather than leaving
a blank one beside the restored ones.

A window the reader closes is dropped from the session, so the next
launch does not put back something they shut. Unless it was the last one:
there would be nothing at all to come back to, and the session file is
the only place an untitled document has ever been. A window closing
because the app is quitting keeps its place, which is the whole point of
the file.

Recents are merged rather than assigned. Every window reports the whole
list, so two of them writing in turn would each undo the other's.

## What was left

- **A tab cannot be dropped onto a window that is behind this one at
  that point.** The pointer decides, and the window under the pointer is
  found by frame, not by what is visible: a target overlapped by the
  source at the drop point is a tie broken arbitrarily. The palette
  command covers what the drag cannot.
- **No drag image and no live preview.** The tab strip uses the
  browser's own drag, so what the reader sees between picking a tab up
  and letting it go is whatever WebKit draws. Tabs in the title bar
  (WP 2.8) is where the strip gets built properly.
- **Two windows each check for updates.** Harmless, and the same answer
  twice; the updater is a window's business today and should become the
  application's.
- **A moved tab is not in "reopen closed tab".** It was not closed, it
  is somewhere else, and reopening it here would be the second copy this
  whole work package is about not making.
