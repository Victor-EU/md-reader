# ADR 0010: WP 1.5 The rest of the dialect

Status: accepted, 2026-09-08. Covers footnotes, the callout type set, the
inline HTML whitelist, the frontmatter properties panel, the Edit-mode
block widgets, and image loading under design 8.

## Footnotes are a composite block, and they render where the file puts them

`[^label]:` opens a composite block, the way a list item does, so the note
holds real blocks — paragraphs, lists, code — rather than one flat string.
That is what lets the body of a note be edited in place like any other
block, and what lets the renderer treat a note as an ordinary container.

A definition may interrupt a paragraph. CommonMark's link reference
definitions may not, and following that rule here would misread the shape
models actually write:

```markdown
The load test finished on Tuesday[^1]
[^1]: Run against staging, not production.
```

GitHub reads that as a footnote and so do we. Design 5.2's rule is the
most plausible intent, and a paragraph that happens to start with a
bracket is not it.

Notes render **in place**, not gathered into a section at the end. GitHub
moves them; we cannot, and would not want to. Every element in this
renderer sits at its own source range in source order — that is what makes
click-to-edit land on the right character, and it is what lets Read mode
render a chunk of a large document without having read the rest of it.
Moving blocks would cost both. Since a document that uses footnotes puts
its definitions at the bottom anyway, the rendered page looks the same.

Numbers follow the order the text first mentions a label, which is
GitHub's rule and the one a reader infers from seeing 1, 2, 3 down the
page. Assigning them is a left-to-right pass, so a chunked render and a
whole-document render agree — the property the goldens rely on. Which
labels exist at all is scanned from the source before rendering starts,
for the same reason link reference definitions are: the reference is above
the definition, and the chunk holding it is rendered long before the one
holding the note.

Anchors go through the same slugger as headings, so a document with a
heading called "Fn 1" cannot take `#fn-1` from a footnote.

## Callouts: the union of the two sets, resolved to canonical names

Obsidian treats `important` as an alias of tip and `caution` as an alias
of warning; GitHub styles both apart. The union is the superset, so both
are canonical here: a GitHub document keeps its five distinct colours and
an Obsidian document loses nothing. Every other Obsidian alias resolves to
one of fifteen canonical names, which is what `data-callout` carries and
what the stylesheet keys on — fifteen rules rather than one per spelling.

A type nobody defined still renders as a callout, styled like a note, with
its own word as the title. Models invent callout types freely, and a
`> [!bananas]` that renders as raw text would be worse than one that
renders as a note.

A fold sign makes the callout a `details` element: `+` is `open`, `-` is
closed. That is exactly what the syntax means, and `details` gives it
without a line of script and without any state for the app to keep.

## The HTML whitelist: an unexpected attribute makes the whole tag literal

Design 5.3 lists what renders. The rule this adds is what happens to the
rest: an attribute outside an element's list makes the **whole tag**
render as literal text, rather than the element rendering with the
attribute dropped. Dropping it silently would show the reader an element
the file does not describe. Showing the tag as text shows exactly what is
written, which is the honest failure, and it is what design 5.3 already
says for `script` and friends.

Lezer emits one node per tag, not a matched pair, so pairing is this
package's job. `HtmlStack` does it once and both views use it: content
accumulates into the innermost open frame, a closing tag closes the
innermost frame of that name and abandons the ones above it, and a frame
nothing closes gives its opening tag back as text. Crossed tags —
`<mark>a <sup>b</mark> c</sup>` — therefore render with the inner `<sup>`
as text in both Read and Edit, rather than the two renderers disagreeing
about a pathological input.

**Pairing stops at the edges of one block.** An HTML block ends at a blank
line, so a `<details>` written the GitHub way

```markdown
<details>

<summary>Click</summary>

Body.

</details>
```

is four blocks, and its tags show as text. The compact form with no blank
lines is one block and renders as a real `<details>`. The reason is
chunked rendering: Read mode renders a long document one top-level block
at a time and would have to look ahead for a closing tag to do better,
which is exactly the property that makes a 1 MB first paint possible. A
rule that holds everywhere is worth more here than one that holds until a
document gets long. Lifting it belongs with WP 2.7, which reworks that
path for virtualization anyway.

In Edit mode nothing is hidden: an allowed tag is **dimmed** and its
content takes the element's styling. HTML in a markdown file is a foreign
body, and a reader editing one needs to see where it starts and ends.
Hiding the tags the way `**` is hidden would also need a reveal unit
spanning the pair, which the reveal rule has no way to express.

## Frontmatter is read line by line, and edited one line at a time

`properties()` reads the block's lines and returns a scalar or a block
sequence per key, each with the exact source range of its own line, or
null when the block holds a shape the panel would misrepresent — a nested
map, a folded scalar — in which case both views show the YAML as it
stands. The YAML is never parsed into a model and never re-emitted, so
quoting, spacing, comments and key order survive an edit to a
neighbouring key. Editing a property replaces exactly its line; adding one
inserts a line before the closing `---`.

Positions come from the state at the moment of the edit, never from the
widget, which can outlive the positions it was built from. A list property
is shown but not edited: a text input is the wrong shape for a sequence,
and offering one would promise an edit this widget cannot make
losslessly. Clicking the panel's background puts the cursor in the block,
where the YAML itself is editable.

## One field for every block widget, and the renderers come from outside

The table widget's state field became `blockWidgetsField`: tables, math,
Mermaid fences, lone images and frontmatter are all built by one walk per
change, which is what the WP 0.4 comment said should happen when the rest
arrived. The incremental machinery — map through the change, rebuild only
the reparsed blocks and the ones whose reveal state flipped — is unchanged.

Math and diagrams are rendered by the **same enhancer Read mode uses**,
handed in through a facet. The widget builds an element with the class
names the Read renderer emits (`mdr-math-block[data-tex]`, `mdr-mermaid`)
and passes it to `enhance.run`. So `editor-core` keeps no dependency on
KaTeX or Mermaid, one implementation serves both views, and a formula
cannot look different in Edit and Read.

Math, Mermaid and image widgets are built only at the top level. A block
replacement covers whole lines, so one inside a list item or a blockquote
would hide the marker that puts it there. Tables keep the unrestricted
behaviour WP 0.4 settled.

## Images: the scope grows to the folder of a file you opened

The asset protocol starts with an empty scope. Opening a document calls
`allow_document_images`, which is the only thing in the app that widens
it, and it widens it only to that document's folder and below. A relative
source resolves against the folder and loads over `asset:`; the CSP allows
`asset:` and `http://asset.localhost` for images and nothing else.

Remote sources are not loaded at all until the reader turns them on for
that document, through `view.remoteImages`. Fetching one tells a third
party that this person opened this file, which is not a decision to leave
to the document. The choice is per document and is never remembered — it
belongs to this reading of this file. A blocked image shows its alt text,
or its source when it has none, and says which case it is; a broken-image
icon would tell the reader nothing.

This also changed the default: before this work a remote `<img>` rendered.
Design 8 says it should not, and now it does not, which is visible in the
`links-refs` and `html-fragments` goldens.

## What the leniency corpus found

`corpus/adversarial/leniency.md` collects the design 5.2 cases that had no
file of their own, and adding it exposed a renderer bug worth recording. A
bare `URL` node — which is what GFM's extended autolink produces for
`https://…`, `www.…` and an email address, and what a link with no closing
paren leaves behind — was being dropped entirely. Real documents were
losing email addresses. It is fixed, and the invariant that would have
caught it is now in the corpus test: **every word of four or more
characters in the source reaches the page**, except inside the handful of
nodes a renderer is entitled to hide, each of which is named in that test.

## What is deliberately still missing

- Comments have a toggle in WP 1.6; here they stay folded away.
- The five-meaning highlight palette and the annotation extractor are WP 1.6.
- Colours for callouts and code are placeholders until the shared token
  theme of WP 1.9.
- Absolute local image paths outside the opened document's folder need the
  folder workspace of WP 2.4 before they can be scoped.
