# ADR 0020: WP 2.2 The semantic diff engine

Status: accepted, 2026-09-09. Covers block extraction, the alignment in
Rust, and the gutter marks that now come from it (design 7.3, plan
WP 2.2).

Design 7.3 opens with the reason this exists: "Line diffs are wrong for
prose. Rewrapping a paragraph shows as a full replacement, a changed cell
shows as a changed row." WP 1.7 shipped the line diff behind a stable
interface and said so. This replaces what is behind it.

## The block is the unit, and the mark is the whole block

The engine answers in blocks; the margin draws lines; the translation is
one for one. A paragraph the agent edited one word of is marked from its
first line to its last.

That is a change of behaviour and it was a decision, not a consequence.
The line diff marked the line the word was on. What that gained in
precision it lost by being about the file rather than about the
document: it marked every line of a rewrapped paragraph, and marked two
unrelated lines when a sentence moved between them. A mark that covers
the paragraph says something a reader can act on -- this is not the
paragraph you read -- and *which* words in it changed is carried
alongside as word runs, for the Review mode of WP 2.3 to draw inline.

The word runs are computed and shipped now rather than in 2.3 because
they are three lines of the same walk and because the pairing pass has
to measure the two texts anyway.

## The kind of a block carries where it is, not just what it is

A block's kind is its leaf's kind prefixed by every container it sits
in: `list>item>paragraph`, `quote>paragraph`, `table>table_row`. Two
blocks pair only when their kinds match in the first pass, so the prefix
is what makes indenting a list item, or pulling a paragraph out of a
quote, a change rather than a move. The words did not change; where they
are in the document did, and that is a thing that happened to the
document.

An ordered list contributes `olist` where a bulleted one contributes
`list`, so converting between them is a change to every item. The
numbers themselves are skipped along with the bullets: renumbering a
list says nothing, and dropping the marks is what makes reordering one
of the plan's four cases work at all.

## Normalizing is per kind, because whitespace is content in some of them

Prose kinds are collapsed: every run of whitespace becomes one space,
the quote marks down the left of a blockquote come off, and the result
is trimmed. That single rule is what makes a rewrap invisible, which is
the case design 7.3 exists for.

Code, math, HTML and frontmatter keep their source exactly. Collapsing
the newlines inside a fenced block would call two different programs the
same program.

## Everything is a block, including the constructs nobody named

The walk goes into containers and reports every other leaf. A construct
the flattener has no name for becomes a block under its own node name
rather than being skipped, because a diff that cannot see a construct
reports no change to it, and that is the one answer a change tracker
must never give.

Two things are deliberately outside every block: blank lines, and the
marks that make the structure. Adding a blank line between two
paragraphs changes the file and says nothing; removing the one that
separates them merges two blocks into one, and that shows.

## No hash on the wire

The plan says blocks are sent "with normalized text, hash, and range".
They are sent without the hash.

The receiving side has the text. Hashing a megabyte of it costs about a
millisecond there, against ten or so in the frontend, and a hash beside
the text it describes is a second source of truth that can only ever
disagree with the first. A wrong one would not corrupt an answer, it
would quietly lose a match -- two identical blocks reported as a change
-- which is the kind of bug that never gets attributed to the field that
caused it. `Block` keeps the contract it has had since WP 0.1.

## The frontend sends the middle

Both sides' block lists have their common head and tail matched off
before the call. This is the same trim the line diff had, moved up a
level, and it is the difference between a keystroke costing a diff of a
paragraph and one of a document: 209 bytes cross the bridge when
somebody types into a megabyte, against 3.4 MB when an agent rewrites
one.

A move cannot hide in a trimmed end. A block in the common prefix is in
the same place on both sides by construction, so it did not go anywhere.

## What the alignment does, in order

1. **Myers over the block keys.** `similar` on `(kind, text)` pairs,
   with the `distance_floor` guard `diff.rs` already had for lines and
   the same bound: past it the whole middle is one region, because the
   answer to a rewritten document is that it was rewritten and Myers
   should not spend a minute agreeing.
2. **Moves.** Blocks left unmatched that are the same block somewhere
   else. This runs before the similarity pass because being the same
   block is a better answer than being alike, and a section that moved
   usually lands beside a paragraph it would otherwise pair with. A move
   is reported once, where it arrived: marking the place it left as well
   would put two marks in the reader's document for one thing having
   happened.
3. **Similarity.** Normalized Levenshtein within a region only, above a
   threshold of 0.5. An edited paragraph is where its old self was;
   pairing across the document would call two paragraphs on the same
   subject the same paragraph. Kinds are *not* required to match here --
   a heading promoted a level and a paragraph made into a list item are
   both one block becoming another, and reporting them as one gone and
   another arrived would be describing the tree rather than the document.
4. **Word diff** inside each pair.

The threshold was tuned against the cases table. Above about 0.6 a
paragraph that gained a sentence stops pairing with itself; below about
0.4 two unrelated paragraphs of English pair with each other, because
prose in one language is more alike than it looks to an edit distance.

Two bounds keep the quadratic pass affordable: a region larger than 64
blocks a side is not paired at all, and a similarity is measured over at
most the first 4000 characters. Two blocks that agree for four thousand
characters are the same block whatever they do afterwards.

## The scan waits for the typing to stop

The change scan was a throttle and is now a debounce. The marks are
mapped through every edit as it happens, so what waits is only the
question of which runs there are -- and asking it in the middle of a
burst answers about a buffer that has already moved on. A result whose
buffer moved under it is dropped; the transaction that moved it has
already asked for another scan.

The buffer's blocks come from the editor's own tree, which it keeps up
to date for the outline, the word count and Read mode. A scan that finds
the parse unfinished takes no answer and tries again, rather than
forcing a parse the reader did not ask for. The version the marks are
measured against has no tree of its own and is parsed headlessly, with
the same parser, which is what makes the two lists comparable.

Both flattenings are kept, two slots, keyed by the `Text` they came
from. Two, because of what happens when a reader says they have seen the
document: the reviewed version becomes the buffer, and the buffer is the
list the scan just made. It is also what makes opening a file cost one
flattening rather than two for a diff that is empty by construction.

## `block_diff` cannot fail

It took `Result` as a stub. Both sides arrive as arguments, so there is
nothing to read, nothing to lock, and no answer but the alignment of
what was sent. The command returns the alignment, and the caller has one
fewer branch that could never be taken.

## The budget, measured

The plan asks for a 1 MB external change end to end in under 200 ms.

| | 100 KB | 1 MB |
| --- | --- | --- |
| Flatten, trim and serialize (WebKit) | 9 ms | 17 ms |
| Flatten, trim and serialize (Chromium) | 4 ms | 38 ms |
| Align (release) | | 9 ms |
| On the wire | 349 KB | 3.4 MB |

The alignment's own numbers, on the same megabyte: 2 ms for a document
rewritten from end to end, 9 for one where every sixth paragraph
changed, 58 for one where half of them did.

The parse is not in that table on purpose. A 1 MB document takes about
200 ms to parse and the scan does not cause it: the editor holds that
tree for three other readers of it, and a scan that arrives early waits
rather than forcing it. The first marks on a freshly opened megabyte
appear when the parse finishes, which was true before this work package
and is measured beside the rest as `firstScan`.

If the wire ever becomes the problem, the move is to send the hashes
first and the text of the unmatched blocks second. At three times inside
the budget it is not worth the round trip.

One shape of input costs more than any of these, and no cheap bound sees
it coming: the same paragraphs in another order. Every block is still
there, so the lower bound the guard reads stays small, Myers runs, and
then finds a long edit script because almost nothing is where it was --
355 ms at a megabyte. The guard cannot catch it, because a lower bound
on the distance is not an upper one, and the alternatives are a wall
clock deadline inside the diff, which would make the marks depend on how
busy the machine is, or refusing inputs by size, which would refuse the
scattered change above as well. Nothing a file watcher delivers looks
like this, the scan is in the background, and the marks arrive a third
of a second later. It is measured and bounded in the budget test rather
than pretended away.

## What was left

**The gutter cannot narrow a mark to the words that changed.** The word
runs are offsets into the normalized text, and normalizing is not
offset-preserving -- a rewrapped paragraph's words are in different
places in the file and the same places in what it says. Mapping back
would mean carrying a per-character map for every block, which costs
more than the marks are worth. Review mode draws the words from the
normalized text, which is what the reader reads; reverting is a block at
a time, which the block's own range already supports.

**A code block indented by the list item it moved into reads as a
change.** Its source really did change, and its whitespace really is
content, so this is the two rules agreeing rather than a bug -- but it
is the one place where a move shows as a rewrite.

**A change mark is not drawn while live preview is rendering the block
it belongs to.** The marks are line decorations and CodeMirror does not
render a line a block widget has replaced, so a changed table row shows
in Source mode, is counted in the badge and is reached by the step key,
and shows in Edit mode only once the cursor enters the table and the
source is revealed. The hole is WP 1.7's; this work package makes it
visible by reporting the row as a block of its own. Both fixes -- a
layer measured from coordinates, or handing the change state to the
widgets -- are a rework of how a mark is drawn, which belongs with the
Review mode of WP 2.3.

**The `start` attribute of an ordered list is not watched.** Changing
`1.` to `5.` on the first item changes what is rendered and no mark
appears, because the marks are what carry the numbering and they are
skipped. Catching it would cost list reordering, which is worth more.
