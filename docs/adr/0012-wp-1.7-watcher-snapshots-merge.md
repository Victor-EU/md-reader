# ADR 0012: WP 1.7 Watcher, snapshots, non-conflicting merge

Status: accepted, 2026-09-08. Covers the folder watcher, the three-way
merge in Rust, the history store, the change marks and the Changes badge.

## The events say where to look, not what happened

The watcher reads the file again after the debounce and compares it with
what it last saw. The filesystem events are used only to decide which
files are worth re-reading.

This falls out of what the events actually are. A tool that saves by
truncating and writing produces a modify, then another modify, then a
metadata change. A tool that saves by writing a temporary file and
renaming it over the target produces a create, a rename, and the
destruction of the very inode a file watch was attached to — which is why
the watch is on the folder, not the file. A tool that writes and then
reverts produces two events and no change at all. Reconstructing the
content from that sequence would mean modelling every writer; re-reading
the file models none of them. It also makes the debounce do real work
rather than just spacing events out: three writes in eighty milliseconds
are one read and one report.

The same comparison recognizes our own saves. `save_document` tells the
watcher the hash it just wrote, so when the event arrives and the file
still has that hash, there is nothing to report. Nothing depends on the
write having come from inside this program — an outside process that
happened to write the same bytes is also, correctly, not a change.

## The two indices `similar` leaves unset

`similar`'s `DiffOp::Insert` carries an `old_index` and `DiffOp::Delete` a
`new_index`, and neither is a position in the alignment. On
`("b\na\n\n", "\n\n\n\na\n")` the Myers ops come back as delete, equal,
insert, where the insert's `old_index` is 1 and the delete's `new_index`
is 3. Read as positions, that puts an insertion inside a deletion, and
applying the result loses a line.

The fix is to walk the ops with our own cursors and read only the index
each op actually states. A fuzz over twenty thousand random pairs across
all three of the crate's algorithms found no case where that reading
fails, and none where the other reading is safe. `line_positions_come_from_walking_the_ops`
pins the input above so that a version bump which changes the convention
is caught in the diff and not in somebody's merge.

## Adjacent edits conflict, and that is the algorithm working

Two changes with no untouched line between them are one hunk. If we
changed line 3 and they changed line 4, there is no order to put the two
versions in that is not invented, so diff3 calls it a conflict. The same
rule makes an insertion immediately before a line the other side changed
a conflict.

This is worth stating because it looks like a bug the first time it
happens: two edits that a human can see are independent are refused.
The alternative is guessing at an interleaving, and the cost of guessing
wrong is a document that says something neither side wrote. Both cases
are in the merge table with a comment saying which rule they are there
for.

## The merge is bounded by an estimate, not a clock

Myers costs O((n+m)·d). For a document rewritten from end to end, `d` is
the whole document and the merge would run for minutes to report what one
hunk already says: all of it changed.

A deadline would bound it, but then the same three inputs could merge
differently on a loaded machine, which is not a property to give a merge.
Instead a cheap pass counts the lines one side has more copies of than
the other. That count is a lower bound on the edit distance and costs one
pass over the lines. Past five thousand, the differing middle becomes a
single hunk.

The bound is deterministic, and it does not fire on the case that matters:
an agent rewriting two sections of a large file has a small edit distance
however large the file is. Measured on a megabyte: 13 ms for scattered
changes on both sides, 9 ms for a full rewrite, against a 200 ms budget.

## Offsets are UTF-16, everywhere

Every position that crosses the IPC counts UTF-16 code units, because the
other end is a `CodeMirror` document and its positions are JavaScript
string indices. Rust counts them at line starts, where the hunks are, so
the conversion is a table built once per document rather than a scan per
edit.

Within a replaced hunk the ends both sides agree on are trimmed to
characters. Changing one word then moves one word, which keeps a cursor
elsewhere on the line where it was and keeps the gutter honest about what
changed.

## Snapshots are content-addressed, and the index is a SQLite file

Ten snapshots of a document whose last paragraph keeps changing cost ten
rows and ten blobs. Ten snapshots that undid and redid the same edit cost
ten rows and two, because the blob is named by the hash of its content.
Taking a snapshot of content the document already has at the top of its
history returns the snapshot that is there, so opening a file the app just
saved does not add a row saying nothing changed.

Retention runs at startup, where the cost lands on nobody: everything from
the last thirty days as it was taken, one a day before that, and then the
blobs nothing points at any more.

The schema carries a `schema_version` table from its first version. The
store on disk is a user's history and it outlives every release, so
migrations only ever append.

## The marks are told, not asked

The change runs are computed by the shell and handed to the editor
through one effect. In Phase 1 that is a line diff against the last
reviewed snapshot; in Phase 2 the same effect carries what the semantic
engine returns from Rust (WP 2.2), which arrives a moment later and from
somewhere else. Having the editor compute its own diff would have made
that swap a rewrite of the marks rather than a change of who calls it.

Between two diffs the marks are mapped through every edit, so a run stays
beside its text while the reader types and the diff catches up on the
pause. The diff itself matches off the lines both versions share at each
end first, so typing a word costs a diff of one line by one line however
long the document is.

They are not in a gutter, which is what the plan asked for and what the
first version did. Seen in the window, a `CodeMirror` gutter sits at the
left edge of the editor, and the measure is centred in the pane: the mark
came out a third of a screen away from the line it was about. The marks
are line decorations drawn in the padding the measure already has, which
puts them beside the text at any window width and moves nothing when the
mode changes — a shifting text column would have cost the property that
Read and Edit show the document in the same place (design 7.1).

## What is not here

**A conflict is not shown, only kept.** Phase 1 keeps the buffer's version
of a conflicting hunk, takes an `external` snapshot of theirs, and says
in the status bar that it set one aside. The widget that offers both
versions with "keep mine" and "take theirs" is WP 2.1. The merge already
returns the conflict ranges, so what is missing is the widget and not the
information.

**A rename out of a watched folder is a removal.** macOS reports a rename
only where the file landed, so a watched file that leaves is found by
looking: anything in a folder the batch touched that is no longer there.
If it landed somewhere we can see, its filesystem id says which file it
became and the tab follows it. If it landed outside every watched folder,
there is nothing to follow and the tab keeps its buffer as if the file had
been deleted.

**The second-process tests are Unix only.** The scenarios all run in this
process too, which the watcher cannot tell apart — it recognizes our own
saves by hash, not by author — so the portable tests cover the behaviour
and the shelled-out ones check that the claim is true rather than only
reasoned about.
