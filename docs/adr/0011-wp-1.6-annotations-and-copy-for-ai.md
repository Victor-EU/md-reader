# ADR 0011: WP 1.6 Annotations and Copy for AI

Status: accepted, 2026-09-08. Covers the four annotation commands, the
comment anchoring rule, notes in the editor's margin, the Read-mode
comment toggle, the annotation extractor, and the three clipboard forms.

## The commands plan, and something else dispatches

Each command is a pure function from an `EditorState` to a change and a
selection. The `StateCommand` that dispatches it is three lines around
that function.

The split earns two things. The round-trip corpus can state the bytes it
expects without running the editor, so a corpus failure means the command
wrote the wrong bytes rather than that the harness and the command agree
with each other. And Read mode can annotate: there is no editor view
there, so the shell applies the plan to the document's own state and
remounts. Without the split, S2 would begin with "switch to Edit mode",
which is not how anyone reads a plan.

## Anchoring is adjacency, and adjacency is whitespace

Design 4.3 says a comment placed directly after an inline element is
anchored to it. "Directly after" is read strictly: only whitespace may sit
between the element and the comment.

```markdown
==the migration== <!-- note: too ambitious -->   ← anchored
**bold** and some words <!-- note: hm -->        ← anchored to nothing
```

The strict rule is explainable in one sentence, survives editing, and is
the same in the extractor and in the editor's margin note, so the note
points at exactly the span Copy for AI names. A looser rule — "the nearest
element", "the sentence" — would be guessing, and a wrong guess about what
a comment is about is worse than no guess: the comment still reaches the
model with its own words, just without a quoted anchor.

A comment on its own line anchors to the block below it, unless that block
is another comment. A note above a note is about the document.

## A comment with nothing selected goes above the top-level block

Not above the innermost block. A line inserted inside a list or a
blockquote has to carry that container's prefix to stay part of it, and an
unprefixed line in the middle of a list is a lazy continuation of the item
above it — the insertion would change what the document means rather than
annotate it. Above the whole list is always valid markdown, and it is
what the extractor then anchors the note to.

## The palette writes a colour and an empty note

Picking a palette colour writes the span and `<!-- meaning:  -->`, and
leaves the cursor between the two spaces. Design 4.3's reason for the
palette is that a colour alone is invisible to a model; leaving the note
for the reader to fill in makes writing the reason the default, not an
extra step. An empty note is still information — the extractor reports it
as the meaning without a reason — and it is one keystroke to delete.

Colouring text that already carries a colour replaces that colour rather
than nesting a second span inside the first. Nesting renders as the inner
colour and leaves the file saying two things about one span.

## Notes are widgets in Edit, and a class in Read

In Edit mode a comment the vocabulary knows is replaced by a chip carrying
the kind and the words, in the margin at widths that have room and inline
at widths that do not. The source comes back the moment the selection
touches it, as it does for every other inline unit, so a note is edited as
the text it is rather than through a form. Hovering a note highlights its
anchor, which is the only way to see an anchoring rule that lives in
whitespace.

In Read mode the renderer emits every comment with `hidden` on it and the
kind and text in their own spans. The toggle is therefore one class on the
article: no re-render, and it works on a document still being rendered in
chunks.

**Known limitation.** A comment that runs over more than one line stays
dimmed source in Edit mode. Decorations that replace a line break may not
come from a view plugin, and the live preview is a view plugin because it
only builds what is on screen. Moving comment widgets into a state field
beside `blockWidgetsField` would fix it; that field is due for work in
Phase 2 anyway, and a multi-line note is longer than a margin chip can
show regardless.

## Tag pairing lives in one function now

WP 1.5 shipped two implementations of "which tag closes this one" — one in
the Read renderer's stack, one in the decoration builder — and they
disagreed about crossed tags until a by-hand check caught it. The
extractor would have been a third, because a coloured span is an
`HTMLTag` pair and the anchor rule has to know where the pair ends.

`pairTags` is now that rule, and the decoration builder asks it. Edit mode
and Read mode reading the same crossed tags differently is a bug the two
views cannot show to the person using them.

## `textOf` skips what the renderer hid

A comment inside a heading was contributing to that heading's id and to
its outline entry. Both are wrong: the comment is folded away, and an
anchor should not depend on a remark. `textOf` now skips any element the
renderer marked `hidden`, which is the definition its name already
claimed.

This changes existing heading ids for headings that contain a comment. No
document in the corpus links to one.

## Copy for AI copies the whole document; the other two follow the selection

The annotations section is about the document, so Copy for AI ignores the
selection and always copies everything. Copy as markdown and Copy as rich
text copy what is selected, or everything when nothing is.

Rich text renders the selected source as its own small document. A
selection that cuts a table in half produces half a table — the honest
result of parsing what was selected, and better than refusing.

## What WP 1.6 does not do

- **Annotating a block from Read mode by clicking it.** A selection is
  required; a caret annotates the block it is in only for comments.
- **Removing an annotation.** Undo does it. A "clear annotation" command
  needs a rule for what to clear when marks overlap, and that rule is
  worth writing when the friction log asks for it.
- **Several notes on one line in the margin** stack downwards by index,
  which is fine for two and crowded for five. Design 12 already lists
  margin layout as a risk with inline bubbles as the fallback; the
  fallback is one media query away.
