# ADR 0019: WP 2.1 The conflict widget

Status: accepted, 2026-09-09. The first work package of Phase 2. Covers
the conflict regions, the widget that offers both versions, and the save
that is held while one is open (design 7.2, scenario S5).

WP 1.7 left this deliberately: "the merge already returns the conflict
ranges, so what is missing is the widget and not the information". This
is that widget, and the state it needs to exist in.

## A conflict is state beside the document, never text in it

The plan's line is "conflict regions are never bytes on disk". The way
to be sure of that is not to be careful about writing them out; it is to
have nothing to write. Their version lives in a `StateField` keyed to a
range of the buffer, and the buffer holds our version and nothing else,
exactly as it did the moment before the write landed.

Everything follows from that. There is no marker syntax to strip before
a save, so `save_document` needs no idea that conflicts exist. Rule 2 --
nothing produces markdown text except the editor transaction path and
the Rust save path -- is untouched, because no markdown text is produced
at all. The round-trip corpus does not have to learn a new construct.
And a document with an unsettled conflict that is closed and reopened
comes back as the file, not as a file with two versions of a paragraph
glued together, which is what the conflict-marker approach costs on the
day something goes wrong.

The version the reader is choosing against is not lost by keeping it out
of the document: an `external` snapshot of the whole write is taken
before any of this runs, as it was in Phase 1 (design 4.4).

## One transaction carries both halves of the merge

`merge3` returns hunks only they touched and hunks both sides touched,
in offsets into the buffer as it stands. Applying the first as a change
set and raising the second in the same transaction is not tidiness. Two
transactions would be two undo steps for one write by one agent, and
between them the regions would name text that had already moved.

That forced the shape of the call. A state field reads the effects of a
transaction against the document as it *will be*, which is the
convention every CodeMirror field is written to, while the merge answers
in offsets into the document as it *was*. So the change set is built
first, with `ChangeSet.of`, and the regions are mapped through it before
they are put in the effect. Doing it the other way -- mapping inside the
field -- would have made this one field disagree with every other one
about what an effect's positions mean.

## Both ends of a region associate to the left

A region has to survive the reader typing, and where they type decides
what it should do.

Text typed at the start of the conflicting lines is more of our version,
so the region grows to hold it: taking theirs should replace it along
with the rest. Text typed at the start of the line *after* the region
belongs to the document and nothing here may delete it. Mapping both
ends with `assoc = -1` gives exactly that, and the pair of tests that
pins it fails if either end is flipped.

## Both choices are undoable, and keeping mine is the reason

Taking theirs is a change, so undo would revert the text on its own --
but reverting the text without the question would leave the reader
looking at their own version again with nothing offering the other one.

Keeping mine is the case that settles it. It writes nothing at all: our
version is already what the buffer says. Without an undo there would be
no way back from it at all, and the version they turned down would be
left only in the history store, which is WP 2.3 and does not exist yet.
A choice with no way back is one a reader makes slowly, and this one
should be cheap to make.

`invertedEffects` covers both directions: undoing a write takes its
questions away with its text, and undoing a resolution brings the
question back. It also has the side effect of putting a keep-mine into
the undo history at all, since a transaction with no changes and no
inverted effects is not an undo step.

## A newer write supersedes an unsettled region it covers

Two writes with no answer between them is a real sequence: an agent
working in a loop. Where the second write covers the same lines, the
first offer is a version of the file that is no longer on disk, and
taking it would put back text the writer has since replaced. So the
newer region wins where they meet.

Elsewhere the older question stands, and dropping every open region on
each write would be wrong for a reason worth writing down: the merge
will not report the older hunk again. By the time of the second write
its base *is* their first version, so both sides agree about that hunk
and it never reaches `conflicts` a second time. Dropping it would lose
the offer silently.

## The save is held, not the document

"Save is held while any conflict region exists and the status bar says
so." Held is the whole of it: the document stays editable, Read mode
still reads, find still finds, and every other document in the window
saves as usual. What stops is the write of this one.

Autosave stops through the same gate that already refuses an unnamed
document and a read-only encoding, so there is one answer to "does the
timer write this?" rather than two. Keeping mine writes no bytes, so
nothing would otherwise tell the timer that the last question had
closed; settling a conflict schedules the autosave the way an edit does.

Cmd+S stays *enabled*. A greyed-out Save with no explanation is worse
than one that says `1 conflict to settle before it can be saved` when it
is pressed. The status bar carries the state without being asked: the
save cell reads `Save held`, and beside it is a count that is the one
cell in the bar which is a button, because it is the one thing in there
that is waiting on the reader.

## Their version is shown as source

The reader is choosing between two pieces of source, one of which they
are looking at in the editor's live preview two lines above. Rendering
theirs as markdown in the panel would make the two harder to compare,
not easier, and would pull KaTeX, Mermaid and the image rules into a
widget that exists to answer a yes or no.

## What is not here

**Read mode has no widget.** The plan says conflict regions become
"editor state rendered by a widget", and that is where it is. A reader
who is in Read mode when a write lands sees the count in the status bar;
pressing it switches to Edit and puts the cursor on the first one, which
is the same thing stepping changes does and for the same reason -- Read
mode has no cursor to put on a hunk.

**No shortcut keys.** Next Conflict, Keep Mine and Take Theirs are in
the palette and the menus with no chord, like Mark Reviewed. The choice
itself is two buttons in the widget, and a reader who has one open
reaches it from the status bar. Three chords for something that happens
once in a session would be three fewer left for something that happens
all the time.

**No Previous Conflict.** Stepping wraps, and a document has a handful
of these at most. Previous Change earns its place because a long
document has many changes and scrolling back is real work; this does
not.

**No "keep both".** Neither the design nor the plan asks for it, and the
two orders it could produce are both inventions. The reader who wants
both has the buffer and their keyboard.

**The buttons are not in the tab order.** They sit inside the editor's
content, where Tab is `indentListItem`; giving them focus would mean
taking Tab away from the document. The palette commands are the
keyboard's way to the same two calls.

## What the by-hand pass changed

Two things the tests had no reason to look at, both about the status
bar, both recorded in
[the run](../manual-runs/2026-09-09-wp-2.1-conflict-widget.md).

The widget's buttons dispatch to the editor rather than through the
shell, so nothing in the shell was saying that a question had been
answered: the bar went on reading `1 conflict to settle before it can be
saved` about a conflict that had just been settled. The line is written
in `applyTransactions` now, off the transaction's own user event, which
is where both roads meet.

And a conflict that lands between a keystroke and the autosave timer it
set does not cancel that timer. It fired, was refused, and replaced the
line saying what had arrived with one about a save nobody had asked for.
`scheduleAutosave` clears the pending timer before deciding whether to
set another, and a refusal from the timer now says nothing at all,
because the bar is already reading `Save held` beside the count.

## The merge cases table grew a column

Design section 10's table of diff3 scenarios has said what the buffer
holds when a write lands since WP 1.7. It now also says what it holds
when the reader has answered every question with "take theirs" -- which
is the thing WP 2.1 made it possible to ask.

One row is new, and it is the row that shows the column is not just
`theirs` spelled twice: a conflict beside a hunk only we touched.
Settling the argument their way leaves our other change where it is.
