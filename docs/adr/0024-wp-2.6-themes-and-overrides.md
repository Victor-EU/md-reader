# ADR 0024: WP 2.6 Themes, fonts and per-document overrides

Status: accepted, 2026-09-09. The remaining three themes, the settings
UI for them, and the reading settings one document may be given instead
of the app's (design 11).

The plan's line is "remaining three themes, remaining bundled families,
per-document overrides keyed by path in app data, the settings UI for
them". The families were already all three: WP 1.9 bundled Inter, Source
Serif 4 and JetBrains Mono, each with upright and italic over Latin and
Latin Extended, and design 11 asks for three. Nothing was missing, so
nothing was added; `theme.test.ts` and `appearance.test.ts` now say so
where a reader would look.

## A token names itself, and the page colours it

Theme one shipped as a JSON file read by three things: the generated
stylesheet, Shiki's fences in Read mode, and the CodeMirror highlighter
in Edit and Source. Both highlighters were compiled against it — Shiki
was handed the light and dark palettes and wrote the hexes onto every
token as `--shiki-light` and `--shiki-dark`; CodeMirror was given two
`HighlightStyle`s of baked colours and `themeType` chose between them.

With one theme that is invisible. With four it is the whole problem: a
fence already on the page holds theme one's colours, and changing the
theme would mean finding every fence and tokenizing it again — in a
virtualized Read pane, for chunks that are not currently mounted, with
grammars that load lazily. The tokens the reader can see would change at
one moment and the ones they scroll to at another.

So neither highlighter holds a colour any more.

Shiki is registered with a theme that is not a palette: each of the
sixteen tokens is given a colour that stands for nothing but itself
(`#000001`…`#000010`), and the render maps that colour back to the
token's name and writes `class="tok-keyword"` on the span. The stylesheet
says `.mdr-code .tok-keyword { color: var(--tok-keyword) }`. CodeMirror
gets one `HighlightStyle` whose colours *are* `var(--tok-keyword)`, so
the two engines are reading the same sixteen variables rather than two
compiled copies of one file.

What falls out of that is the feature. Changing the theme, the
appearance or the paper is one attribute on the root element and no
render at all: the same spans resolve to the new palette. The browser
golden proves it — both panes are built once in the default theme and
then read again under each of the other three, with an assertion that
not one element was replaced, and with Read and Source still agreeing
character by character in every theme.

It also removed the dual-theme Shiki output, `swapCode`'s round trip
through `innerHTML` (tokens are built as nodes now, so nothing from a
document is parsed as markup), and one of the two highlight styles.

## Four themes in one stylesheet, chosen by an attribute

The alternative was a stylesheet per theme and a `<link>` swap, which
costs a flash of the old palette while the new one loads and a second
copy of every rule to keep in step. All four are generated into one
file, each fully qualified by `:root[data-theme="…"]`, which is 30 KB
and switches instantly.

The bare `:root` block stays, and is the exception: Rust shows a window
as soon as it is placed, before any script has run, so there is a frame
with no attributes on the root element. That block is the default theme
in light, with a `prefers-color-scheme` companion for dark, exactly as
before. A reader who chose one of the other three sees one frame of
theme one on the way in. That is the same glitch the appearance already
had, and the fix for both is the same future change — Rust stamping the
attributes into the webview before it loads — which is not this WP.

Ordering matters and is deliberate: the boot block and its media query
come first, so a theme's own block (equal specificity, later in the
file) wins the moment the settings arrive.

## What "curated" has to mean when there are four

Four themes, two appearances, four papers is thirty-two combinations,
which is exactly the number at which one of them ships unreadable. The
test suite now holds every theme to a contrast floor, per role rather
than one number: AAA for the page's ink on its paper and for the
chrome's own text, AA for code in a fence and for muted text and
accents, and the large-text floor for a comment (which is meant to be
quieter) and for callout colours (which are a bold title and a four-pixel
bar).

Theme one did not pass. Its light palette had a comment at 2.6:1 on the
cream paper and six more tokens below 4.5:1. Each was darkened along its
own hue by the smallest amount that clears the floor — the largest move
is `#b8622a` to `#a25524` — so the theme looks like itself and is
legible on all three light papers. The code golden is the diff.

The five note colours are exempt, and have to be: design 4.3 writes them
into the file as literal hexes, so they belong to the document rather
than to the theme. Every theme's light palette is pinned to the
annotation palette by an equality test instead, which is stronger than a
contrast floor and is what keeps a coloured highlight and a "remove:"
comment the same red.

The three new themes are Slate (cool grey chrome, the familiar editor
colours), Ink (near-monochrome chrome, deep low-chroma code, the most
legible of the four) and Grove (warm sage, greens and golds, as little
blue as a legible palette can manage).

## A document is given a page, never a window

Design 11: "a per-document override is stored in app data keyed by path,
so a reader can give one report a serif and a wider measure without the
file knowing." The override covers paper, family, size and measure —
what the page is — and deliberately not the theme or the appearance,
which dress the chrome. A window whose toolbar changed colour as the
reader moved between tabs would be answering a question nobody asked.

It is kept in `overrides.json` beside the settings and the session,
newest first, capped at two hundred, and an override that says nothing
is removed rather than stored. Every field is optional and means only
what it says: a document given a serif still follows the app's size, so
changing the app's size moves it.

The shell asks Rust for a path's override wherever a document gains one
— opening, restoring, a save-as, a tab arriving from another window —
rather than caching a table. A document belongs to one window (WP 2.5),
so a cache could only ever be stale for a path this window does not
have; asking is one small call on a path that is already being read from
disk, and it is always right. A rename moves the override with the file,
because it is the same document under another name.

Zoom follows the same rule as everything else: `Cmd+=` moves the
document's own size when it has one, and the app's when it does not.
Either way the type on the screen changes, which is what the key means.

## The panel is where the document is

The settings tab edits the app, and it is the wrong place to give one
report a serif: the moment it is in front, the report is not. So the
reading settings have a second home — a panel under an `Aa` button in
the toolbar, over the page it is about, so every change previews itself
on the real document. It opens on the document's own settings when it
has some and on the app's when it does not, and the line under the scope
switch says which of the two the controls are writing to.

The theme picker stays in the settings tab, where the app's own
preferences are, with each theme wearing itself: the paper it would give
this page, its chrome, its accent and three of its code colours, written
inline from its own file because a theme that is not on has no variables
to be read from.

## The settings are the app's, so every window hears them

`save_settings` now emits to every window. Without it, picking a theme
in one window would leave the one next to it in the old one until the
next launch — invisible with one window, and the first thing a reader
would notice with two. The window that asked hears it too and applies
what it already applied, which costs nothing.

This is the one event in the app that is deliberately untargeted. WP 2.5
registered every listener as its own window, because an untargeted
listener receives every emit, addressed or not; the settings are not a
window's, so they are sent to all of them and `main.ts` says why.

## What was left

- A reader on a non-default theme sees one frame of theme one at launch,
  as described above.
- The reading panel has no drag region of its own and closes on any
  press outside it, including on the window's own title bar. That is the
  ordinary behaviour of a light-dismissed panel and nobody has to be
  told about it.
- An override is keyed by the path as the reader opened it. A file
  reached through a symlink and through its real path is two documents
  to this store, as it is to the session and the watcher.
- Overrides accumulate for paths that no longer exist. The cap is what
  bounds it; nothing prunes by asking the disk, because a file on an
  unmounted drive is not a file that is gone.
