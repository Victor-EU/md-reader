# By hand: WP 1.9, theme one and typography

2026-09-08, macOS 15.5 (Darwin 24.5.0), Apple silicon.

## How this run was done, and what that costs

The intended path — a `pnpm tauri dev` window, driven with AppleScript
and captured with `screencapture` — was not available. Screen capture
returned the desktop picture with no windows on it and System Events
reported zero windows for every process, including Finder, which is what
macOS does when the shell has neither Screen Recording nor Accessibility
permission. The WP 1.8 run had both. Nothing about the app changed; the
permissions did.

So the window was looked at another way: a scratch page served by the
Vite dev server that mounts the real `App` component over the fake IPC,
in the same shape `shell.browser.test.ts` uses, with the sample document
already open. That is the real shell, the real read view, the real
editor, the real stylesheet and the real fonts. What it is not is
WKWebView: this ran in Chromium. Both engines are covered by the
automated browser tests, including the code-colour golden, so what is
untested by hand here is whether WebKit renders these particular pages
differently from Chromium — not whether the code works in it.

The harness was deleted after the run.

## What was checked

**The four papers, light and dark.** White, cream, yellow pad and black,
each with the chrome around it. The black paper in a *light* window is
the case the design calls high contrast: the page goes dark, the toolbar
and tab strip stay light, and the code on the page switches to the dark
palette. Confirmed by reading the computed variables as well as looking:
`--page-bg #121212`, `--bar-bg #f1efec`, `--tok-keyword #d98cc9`.

**The three families.** Inter, Source Serif 4 and JetBrains Mono all
resolve to the bundled faces rather than a fallback —
`document.fonts.check` says yes for all three, and twelve faces are
declared. Source Serif at the reading sizes is the one worth having.

**The type scale and the measure.** At 22px with a 52-character measure
the four heading levels stay apart and the page still reads as a page.
The measure slider moves the column live.

**Code in three modes.** The same document's fences in Read, Edit and
Source. Comment grey, keyword plum, string green, number amber, type
teal, function blue — the same in all three, on both palettes. Source
mode is set in the monospace whatever the reading family is; Edit mode
is in the reading family, because it is the document.

**The fence's chrome.** The language label sits top-left in muted small
caps and is the info string the file wrote (`ts`, `rust`, `python`); a
fence with no language gets no label. The copy button is quiet until the
pointer is on the block, copies exactly the code, and says "Copied" on
itself rather than in the status line.

**Settings as a tab.** Opens on Cmd+comma, appears in the strip with no
dirty dot, has no document behind it — the mode switch greys out and the
annotation commands are disabled while it is in front. Only ever one:
opening it again focuses the one that is there. Closing and reopening it
works, and it comes back in its own place with the session.

**Zoom.** Cmd+= and Cmd+- move the reading size along the scale and stop
at the ends with a status line that says so; Cmd+0 returns to 16px. The
settings tab's stepper shows the same number, because it is the same
number.

## What this found, and what was done about it

**`==marked==` was unreadable on the black paper.** Pale yellow ground
under pale ink: the highlight came from the chrome's palette, which stays
light in a light window. Fixed by giving the page its own `--mark`,
which follows the paper. The same fault applied to every page rule that
borrowed a chrome colour, so `--page-border`, `--page-muted` and
`--page-accent` were added with it — twenty-one rules in the page section
now name the page's colours rather than the toolbar's.

**Table stripes and inline code were the wrong grey on coloured paper.**
Both used the chrome's hover colour, which is a grey band on a yellow
page. Inline code now takes the paper's own code ground; the stripe is
mixed from the page's ink at 5%, so it works on all four papers.
Numerics in tables are now tabular, which design 11 asks for and this
run noticed was missing.

**The mode switch showed Read as selected on the settings tab.** The tab
carries a mode whether or not it has a document. The toolbar now asks for
the document.

**Two annotations on neighbouring lines overlap in Edit mode's margin.**
Three chips drawn on top of one another, none readable. This is a WP 1.6
defect and not a colour one — the colours are right — so it was left
alone and spawned as its own task with the reproduction. The margin rule
steps notes by a fixed 1.7em, which cannot hold notes that wrap.

**Shiki's first tokenization after loading a grammar is sometimes
wrong.** Found by the code-colour golden, which failed about two runs in
five on WebKit. The whole second line of a fence came back painted in the
first line's colour — the token boundaries were right, the scopes were
not. It reproduces with Shiki's own bundled themes, so it is not theme
one, and it only ever affects the first call: over roughly two hundred
samples no later call was wrong. The enhancer now tokenizes the first
block through a new grammar once and discards it. Six runs of the golden
across both engines since, all green.

## Not checked

- WKWebView, for the reason at the top. The automated browser tests do
  run on WebKit.
- The system appearance actually following the OS. The harness reads
  `prefers-color-scheme`, and the unit tests cover `resolveAppearance`,
  but switching macOS between light and dark and watching the window
  needs the window.
- Whether the bundled fonts survive `tauri build` into the installer.
  The Vite build copies twelve `.woff2` files into `dist/assets`, which
  is the input to that; WP 1.12 is where the installer is checked.
