# By hand: WP 2.8, tabs in the title bar

2026-09-09. Against the installed release build — `pnpm tauri build
--bundles app`, copied to `/Applications/MD Reader.app` — driven with
real keystrokes and a real mouse (`CGEvent` move, press, drag, release),
with screenshots of the window measured pixel by pixel.

## The setup

Nine markdown files in a scratch folder, named from `alpha.md` to
`theta.md` with one called
`a-rather-long-file-name-for-the-strip.md`, so that a strip full of tabs
has both kinds in it. `session.json` was removed first, so the run
starts from an empty window, and it and `settings.json` were put back
afterwards.

Geometry was read out of the screenshots rather than judged by eye: the
three system buttons are found by colour, the strip's lower edge by the
step from the chrome's colour to the front's, and both are reported in
window points.

## The two it found

**Leaving full screen left the tabs under the buttons.** The room kept
for them is given back when the window goes full screen and taken again
when it leaves, and the only news of either the page gets is the window
changing size. Asking macOS at that moment is enough on the way in and
not on the way out: it clears the flag at the end of the animation that
follows the last resize, so the answer was still "yes" and the tabs sat
under the traffic lights until the window was next resized by hand. The
question is now asked again as the window settles — see
`watchFullScreen`, which has the timing written down and a test for the
run it schedules.

**The tab in front could be pushed off the end of the strip.** Tabs now
shrink to a floor before the strip scrolls, and once it is scrolling, a
window dragged narrower pushes the tab the reader is in out of sight.
Bringing it back was tied to the tab changing, and no tab had changed. A
`ResizeObserver` on the strip is the second reason to bring it back; the
browser test narrows the pane and fails without it.

## What could not be checked here

- **Reorder by drag.** A synthesized drag reaches `dragstart` and
  `dragend` but never delivers `drop`, so every attempt read as a tear
  into a new window — which is the right answer for a tab dropped on
  nothing, and is itself checked above. Reorder has a browser test
  (`does not tear a tab that was dropped back on the strip`). The same
  limitation was recorded in the WP 1.3 run.
- **Mixed-DPI moves.** This machine has one display, built in and
  Retina. There is no second screen to drag a window onto.
- **Windows.** No machine, as since 2026-09-08.

## What the run found that is not this work package's

A window moved and then quit with Cmd+Q comes back where it was before
the move. The frame is written down with the window's contents, and
Cmd+Q on macOS reaches the app only as `RunEvent::Exit` — too late to
ask the webview for anything, as the comment on `before_exit` has said
since WP 1.8 — so a move with no tab change behind it is never recorded.
This run made it easy to hit, because dragging the strip is now the way
you move the window. It belongs with the session, not with the title
bar.
