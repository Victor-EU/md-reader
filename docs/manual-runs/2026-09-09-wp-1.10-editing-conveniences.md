# WP 1.10 by-hand check — editing conveniences

Date: 2026-09-09. macOS only; Windows is parked with no machine to run
it on.

## How this was driven

Unlike the WP 1.11 run, this one was driven by hand for real. Screen
Recording and Accessibility are now granted, so `screencapture` returns
the app's own window and System Events delivers keystrokes and clicks to
it. Every line below is the real app — `pnpm tauri dev`, WKWebView, the
real IPC, the real Rust save path, real files on disk — with real keys
pressed and real pictures taken.

The one exception is marked: a temporary `keydown` probe was appended to
`main.ts` to answer why Cmd+I did nothing, and reverted from a scratchpad
backup afterwards.

Document: `scratchpad/hand/notes.md`, rewritten between runs.

## Two bugs the by-hand pass found

### Cmd+I did nothing

Bold, code and link worked; italic did not, and the palette's Italic did.
The probe showed the key reaching the window intact
(`key="i" code=KeyI meta=true`), identical to Cmd+B.

`@codemirror/commands`' `defaultKeymap` binds `Mod-i` to
`selectParentSyntax` with `preventDefault: true`. The editor's keymap is
on the content element and the shell's is on the window, so the editor
saw it first, prevented the default, and `App.svelte` — which leaves a
key the editor has handled alone — never ran the command. The selection
expanding to the whole enclosing paragraph, visible in the screenshots
before the fix, was `selectParentSyntax` doing its job.

Fixed by taking the binding out of the keymap in `state.ts` rather than
trying to out-rank it, and guarded by a new test in `commands.test.ts`
that walks every key the editor claims and fails if the shell claims it
too. Putting `Mod-i` back makes that test fail with
`Mod-i is both the editor's and edit.italic`.

No unit test could have caught this: they call the command directly, and
the shell's key tests dispatch on the window, where CodeMirror never
sees the event. There is now a browser test that presses Cmd+I on the
editor's own element.

### A selection of a line break was wrapped in `**`

An early harness click left the newline between two blocks selected.
Cmd+B wrapped it, writing `**` on one line and `**` at the start of the
next — four asterisks that render as themselves. The mark now trims the
whitespace at a selection's edges and refuses a selection that is
nothing but whitespace.

## Spell check needs something the app cannot set

`spellcheck="true"` is on the content element, `autocorrect` and
`autocapitalize` are off with it, and a browser test asserts all three.
On macOS that is necessary and not sufficient: WKWebView also consults
the application's `WebContinuousSpellCheckingEnabled` user default, which
is off for a new app, and nothing was underlined.

With

```
defaults write io.github.victor-eu.mdreader WebContinuousSpellCheckingEnabled -bool true
```

and a relaunch, misspellings are underlined as they are typed, including
in text typed before the relaunch once it is edited. Photographed.

Setting that default from inside the app means `NSUserDefaults` through
objc, and this workspace denies `unsafe_code`. The options are a native
Edit ▸ Spelling ▸ Check Spelling While Typing menu item, which is the
standard AppKit control for exactly this default and would come with the
menu work; or a narrow, reviewed exception to the lint. **Carried to WP
1.12**, where the menus are built anyway. Until then the app enables
spell check and macOS may or may not act on it.
