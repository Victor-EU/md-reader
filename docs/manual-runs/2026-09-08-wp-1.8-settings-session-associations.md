# WP 1.8 by-hand check — settings, session, single instance, associations

Date: 2026-09-08. macOS only; the Windows half of this work package is
parked with no machine to run it on.

Two builds were used, because two of the deliverables need different
ones. Session restore, the close round trip and the quit behaviour were
checked against `target/debug/mdreader-desktop` with the Vite dev server,
which is the fastest way to get a real WKWebView window. File
associations and the OS open events need a real bundle, so those ran
against `pnpm tauri build --debug --bundles app`, registered with
`lsregister -f` and driven with `open -a`, which is what "Open With" does.

Files are in the session scratchpad: `alpha.md` with two headings,
`beta.md`, `gamma.md`, `delta.md`.

## Findings

**Cmd+Q on macOS never reaches the window.** Instrumenting the run loop
showed a Cmd+Q producing `RunEvent::Exit` and nothing else — no window
close, no exit request. A tab switch made immediately before it was lost.
The `ExitRequested` handler that asks each window to finish is correct
and fires on the platforms that send it, but macOS's predefined Quit item
goes through `NSApplication.terminate:` and skips the event loop.

Fixed as far as it can be without owning the menu bar: the shell now
pushes a structural change at the end of the turn rather than after a
pause, so what Rust holds is current, and `RunEvent::Exit` writes it. Re-checked:
the tab switch survives. What is still exposed is text typed into an
untitled document in the half second before a Cmd+Q. Closing that means
replacing the predefined Quit item, which is build plan section 8.

**A launch document arrives before the app exists.** A cold Open With
dropped the file. The trace was `RunEvent::Opened` *then* `setup`, so the
per-window queue it was meant to land in had not been created yet. Fixed
with a `static` that holds paths until `start` has somewhere to put them;
re-checked cold and the file opens after the restore.

**A restored untitled document lost its dirty dot.** It came back clean,
because the constructor takes the restored text as its base. Nothing on
disk holds that text, so the dot belongs on it. Fixed by giving a
restored untitled document an empty base, and leaving `reviewed` where
the document is so the Changes badge stays quiet.

## Not checked

- **Pinning a tab.** Only reachable by double-clicking the tab, and
  synthesized clicks do not produce a `dblclick` in WKWebView. Pinned
  state through the session is covered by the browser tests. The wider
  point — that pinning is not a registered command and so is in neither
  the palette nor the keymap — belongs to WP 1.3.
- **Windows.** File association registration, the single-instance
  callback and argument forwarding are written to the documented API and
  left for the parked Windows gate.
- **Being the default handler for `.md`.** Registration puts the app in
  the Open With list, which is what design 8 asks for. Which app owns the
  double-click is a binding the reader makes, and not ours to change on
  their machine.
- **Settings end to end.** Nothing in the window changes a preference
  yet, so `settings.json` is never written by an ordinary session. The
  store round trip is covered in Rust, the shell's path in the browser
  tests.

## Also found, not this package

The sidebar outline keeps showing the previous document after switching
from a Read-mode tab to a Source or Edit one. `refreshOutline` bails
while a Read view is mounted, because in Read mode the view feeds the
outline itself, and the view is only torn down afterwards. A fix at the
teardown makes a browser test pass but not the real window, and the two
observations do not yet fit together, so it is left as its own task
rather than half-fixed here. It is a WP 1.4 defect and predates this
work.

## False alarms

- AppleScript's `keystroke "1" using command down` does not reach the
  app; the event arrives without a usable `code` or key. `key code 18
  using command down` works. Cmd+1 was fine all along.
- Copying a freshly built binary into the bundle replaced a build that
  had the frontend baked in with one that expects the dev server, which
  made a run look as though the whole boot sequence had failed.
