### With autosave on, which is the default

| # | Step | Result |
|---|---|---|
| 1 | Type inside the paragraph, agent writes in the same breath | Same widget, `1 change merged in · 1 conflict to settle` |
| 2 | Wait out the 800 ms timer, and four seconds more | Did not write. Disk still the agent's, byte for byte |
| 3 | `Keep mine` | `Kept your version`, and the timer wrote our line a moment later |

The other side of that race is worth one line, because it is the design
working as written rather than a defect. Let the 800 ms pass first and there
is no conflict to have: the edit is on disk, the buffer is clean, and the
agent's rewrite — built from what it read before — is an ordinary external
change that takes the paragraph back. Design 6.6's reason for keeping the
window short is exactly this, that "the file on disk is the channel to the
AI"; what protects the reader afterwards is that the overwrite arrives as a
marked change rather than as silence — `Changes 3`, `3 changes merged in`,
and a bar in the gutter beside the paragraph it took back. Stepping to it is
Cmd+Alt+G and undoing it is Revert This Change, which the WP 2.3 run
checked.

One thing noticed on the way out: closing a tab with a conflict still open
says `Closed plan.md with unsaved changes · reopen the tab to get them
back`, so the close is not silent about what it is setting aside. Whether
reopening brings the question back with the text was not checked here.

## The external writer, from the manual protocol

Plan 7.5 asks for "a shell loop that rewrites the file every two seconds
while typing" before each gate. Ten writes, two seconds apart, against ten
sentences typed into the same document over the same twenty seconds, with
autosave on.

What happened is worth writing down, because it is the app being asked to
choose and choosing right. Autosave wrote our sentences to the file between
bursts; each of the writer's rewrites was built from the original and so
*deleted* them again. That is the merge case "they deleted the region we are
editing", and it is a conflict — reported as a `MINE` band holding all ten
sentences over a `THEIRS` panel holding nothing.

| Check | Result |
|---|---|
| The ten sentences after twenty seconds of being overwritten | All present, in order |
| The file on disk | Byte-identical to the writer's last version. Not truncated |
| The app | Still up, still responsive |
| `Keep mine` | Wrote back our paragraph *and* the writer's heading. Nothing lost |

--workspace`: **150 tests**, green in debug and again in release. `pnpm
check`: 708 files, 0 errors, 0 warnings.

**Merge property tests.** Seven properties in `crates/core/src/diff.rs` and
`document.rs`, 256 generated cases each by proptest's default: the edits
turn the old text into the new; a clean buffer takes the whole of an
external write; the same change on both sides is quiet; an unchanged file
changes nothing; the result is the same with CRLF; changes and conflicts are

cases** — adjacent edits, whitespace-only external changes, a full rewrite,
they deleted the region we are editing, one conflict not holding up the rest

**Semantic diff cases.** A table of **12** in `crates/core/src/blocks.rs`,

heading promoted, and a paragraph replaced by an unrelated one. A second

## What the run found

Nothing that is a defect. Two things were checked against the code before
being written off, and both are deliberate:

- **Cmd+S clears the change marks**, where "Mark reviewed" is the command
  named for it. This is `markSaved(written, seen)`: an explicit save passes
  `seen: true` because the reader was here and pressed the key, and an
  autosave passes `seen: false`, so marks on a write that arrived from
  somebody else are never cleared by a clock. Design 4.4's "last reviewed"
  pointer is advanced by both, and only by a save the reader asked for.
- **The empty `THEIRS` panel** in the writer-loop run is the correct report
  of a side that deleted what we are editing, not a missing value.

The `Changes` badge counts the reader's own typing as well as the agent's,
which is already queued as its own piece of work and is not new here.

## What could not be checked here

- **Windows.** No machine. S5 and S6 are unrun there, and so are the bench
  numbers under WebView2.
- **The beta.** A build in front of a handful of people who are not the
  developer is the fourth criterion and cannot be done by an agent.
- **The bench numbers are not from WKWebView.** Plan 7.4 asks for the
  harness to run in two places: Vitest browser mode for the inner loop, and
  inside the real app behind a `--bench` flag, "because the budgets are
  promises about WKWebView and WebView2, not about Playwright's browsers".
  That flag does not exist. Everything in the bench table above is
  Playwright's Chromium and WebKit; the margin is wide enough that the
  conclusion is unlikely to change, but it has not been measured where the
  promise was made.
- **This is a developer laptop**, not one of the two pinned machines plan
  7.4 asks for. The numbers are indicative of the margin rather than a
  regression baseline.
