# WP 1.6 by-hand check — annotations and Copy for AI

Date: 2026-09-08. Build: the real desktop window under `pnpm tauri dev` —
WKWebView, the OS open panel, the system clipboard. A few checks that need
a pointer or a drag were done against the same frontend served at
`localhost:1420` in a browser, and are marked as such: AppleScript cannot
move the mouse, and the app's own window cannot be hovered from a script.

The document is in the session scratchpad: frontmatter, a highlight with a
note, a struck bullet, four coloured spans (three palette colours and one
the reader picked), a block comment above a paragraph, a comment anchored
to nothing, a comment outside the six-word vocabulary, and a note that
runs over two lines.

## Findings

**Select All in Read mode then Highlight does nothing but say so.** The
ends of that selection are element containers rather than text nodes, so
the offset map cannot place them, and the command refuses rather than
marking a range it guessed. Refusing is right — marking the wrong span
would be worse — but a reader who tries it gets a message and no action.
Marking a whole document as one highlight is not a real use, so this is
left as it is.

**The hover marker was a tint alone, and a tint over a highlight is
invisible.** Found by hovering a note whose anchor was `==…==`: the blue
at 18% over the yellow read as nothing at all. Changed to a lighter tint
plus a 2px underline in the link colour, which shows on any ground.

**The kind and the words ran together in the margin form.** The chip is a
flex row inline, where a gap separates them, and a block in the margin,
where the gap does nothing. Fixed with a margin on the kind.

**Comments outside the vocabulary were staying hidden when the toggle was
on.** The toggle says "Show Comments", so it now shows them too, as their
own source. An annotation gets a chip; anything else gets the dimmed text
it is.

## Not checked by hand

- **The hover underline at full size in the app window.** AppleScript
  cannot move the pointer and the browser pane the check ran in is small.
  Confirmed by computed style (`inset 0 -2px 0 0 rgb(42,106,217)`) and by
  the browser tests in both engines, seen small rather than at reading
  size.
- **The toolbar's `mousedown` guard in Read mode.** It exists so a button
  press does not collapse the page selection before the command reads it.
  Reasoned and standard, but a real pointer press in the app window is the
  only way to observe it, and that is what cannot be scripted here.
- **Drag and drop from Finder**, still open from WP 1.3. A real Finder
  drag cannot be synthesized.
- **Windows and WebView2**, parked: there is no Windows machine.
