15.5 (Darwin 24.5.0), Apple silicon, against commit `f7032b7` plus the two
fixes this run produced.

## What the run found

Two defects, both in the parts of the app a scenario touches and nothing
else does. Both are fixed and both have a test that fails without the fix.

### Finding 1. A click below a table or a diagram landed on the wrong line

Reproduced in Edit mode on the fixture: clicking the word "order" put the
caret in "brief", one line below. Above the table every click was exact;
below the table and the diagram it was one line out, and in Source mode —
which has no widgets — the status bar's `Ln`/`Col` agreed with the
pointer to the character.

The cause is that a block widget's height is the height of the element the
editor was handed, and **a CSS margin is outside that element's box**. The
preview theme gave the table `0.4em 0`, the diagram and the frontmatter
panel `0.2em 0`, and a lone image `0.3em 0`. Every one of those moved the
text below it down by an amount the height map did not know about, and the
error added up: measured against the DOM in both engines, 14 px of drift
after the table, 22 px after the diagram — most of the 25.6 px that is one
line at the default size. A document with several diagrams would be out by
several lines.

The fix is that the spacing is padding, which is inside the box the editor
measures. The four blocks keep the space they had. Residual drift is 1 px
in Chromium and 2 px in WebKit, which is the leading inside a line box and
not a disagreement about where the line is.

The regression test is `block widgets and the lines below them` in
`packages/editor-core/src/preview/blocks/widgets.browser.test.ts`: a
document with all four widget kinds, and a click on each of three lines
below them. It fails on the old theme in both engines, by exactly one line.

### Finding 2. A note attached to a highlight was invisible to Copy for AI

S2 in one gesture: select a paragraph, `Cmd+Shift+H`, `Cmd+Shift+M`, type
the reason. The second press is handed the selection the first one
wrapped — which is now the *inside* of the marks — so the note landed
between them: `==...<!-- note: too ambitious --> ==`.

The editor drew it as a margin note, so it looked right. But the
extractor's rule is that a comment belongs to the element **before** it,
and it does not descend into a mark, so `Copy for AI` listed four
annotations and none of them carried the reader's words. `list_annotations`
over MCP reads the same extractor, so the note was invisible to S7 as well:
the one sentence in the document that was addressed to a model was the one
sentence a model could not see as an annotation.

The fix is in the comment command: a note about a span the selection
exactly fills goes *after* the mark, never inside it, stepping out of `==`,
`~~` and a colour span in turn. A note on part of a mark still goes where
it was typed. Re-run afterwards, the same four presses produce
`4. Highlight, "We will do all of this…" — note: too ambitious, cut to two
weeks`.

### S7. Agent reads the human's markup directly

The client is **Claude Code**, configured from the app's own palette
command: `Copy Agent Client Configuration` puts

```json
{ "mcpServers": { "md-reader": {
    "command": "/Applications/MD Reader.app/Contents/MacOS/mdreader-desktop",
    "args": ["--mcp-stdio"] } } }
```

on the clipboard, and that file — nothing else, no port, no token — is what
`claude --mcp-config … --strict-mcp-config` was given. The prompt was one
sentence: find the document the reader has open, read it and the marks they
have left on it, do what their notes ask, and write the new version back
under the name `claude`.

## What is left

**The v1 release candidate is not cut, and should not be.** Three things
stand in front of it, none of them this run's to decide:

- The Phase 1 gate wants two weeks of the developer's own use with a
  friction log. Not started.
- The Phase 2 gate wants a beta build in front of people who are not the
  developer. Not started.
- `release.yml` builds a `.dmg` that Gatekeeper will refuse on any machine
  but this one until somebody enrols in the Apple Developer Program
  ($99/year, days to weeks). `docs/release.md` has the steps; none of them
  can be taken from here.

Everything the repository *can* do for a release is already true: the three
manifests agree on one version number and a test says so, the tag-driven
workflow exists, and the updater manifest is generated. What is missing is
a decision and two accounts.

**Windows.** Unchanged since 2026-09-08 and unchanged by this run. The
`--mcp-stdio` bridge is the part of Phase 3 most likely to behave
differently there — the release binary is a GUI subsystem process with no
console — and it has no machine to be tried on (ADR 0028).
