# WP 1.12 by hand — packaging and the dogfood build

2026-09-09. macOS 15.5, Apple silicon. The **installed release build**,
not `tauri dev`: `pnpm tauri build --bundles app`, then
`open target/release/bundle/macos/MD Reader.app`. Driven with real
keystrokes and photographed with `screencapture`.

That distinction matters here more than in any previous package. The
updater is wired only when `isTauri() && import.meta.env.PROD`, so a dev
build cannot exercise any of it.

## What was checked

| # | Check | Result |
|---|---|---|
| 1 | The bundle builds and runs from `/Applications`-style launch | pass |
| 2 | `THIRD-PARTY-NOTICES.md` is inside the `.app` | pass |

## 1–4 — the bundle

`MD Reader.app` opened, restored the tab from the WP 1.10 run, and said
*Picked up where you left off · 1 tab*. The notices file is at
`Contents/Resources/THIRD-PARTY-NOTICES.md`, which is what
`THIRD-PARTY-NOTICES.md` said this package had to arrange.

`Info.plist` has `NSHumanReadableCopyright`,
`LSApplicationCategoryType = public.app-category.productivity`,
`LSMinimumSystemVersion = 12.0`, and the three markdown extensions under
`CFBundleDocumentTypes`.

## 5, 6 — the quiet rule, against a real 404

The endpoint in the config points at a repository that does not exist
yet, so every check fails. That turned out to be the ideal test of the
rule the package is built around.

- **Automatic**, ten seconds after launch: nothing. The status bar still
  read *Picked up where you left off · 1 tab* twenty seconds in, and no
  update cell appeared.
- **Manual**, from the palette: *Could not check for updates — Could not
  fetch a valid release JSON from the remote.*

Same failure, same code path, and the only difference is whether somebody
asked. That is the whole design of `describeUpdate` versus `reportCheck`,
and this is the first time it has been seen against a real network.

## 7, 8 — where the commands are

`Cmd+Shift+P` → "check for up" lists **Check for Updates… · Help**, the
first entry in the new menu group. Settings ▸ About reads **MD Reader
0.1.0** with a *Check for updates* button; the version comes from Tauri's
`getVersion()`, so it is the bundle's, not a constant in the source.

## 9, 10 — the release chain, end to end

`pnpm tauri build --bundles app` with `TAURI_SIGNING_PRIVATE_KEY` set
produced `MD Reader.app.tar.gz` and `MD Reader.app.tar.gz.sig`. Feeding
that directory to the manifest builder:

```
pnpm release:manifest --version 0.1.0 \
  --base-url https://github.com/victor-eu/md-reader/releases/download/v0.1.0 \
  --out latest.json darwin-universal=<dir>
```

produced a `latest.json` whose `darwin-universal` entry carries the
signature from the `.sig` file and the URL
`.../MD%20Reader.app.tar.gz` — the escaping the product name's space
makes necessary, which was a guess in the test and is now a fact.

## 11 — the `.dmg` is blocked on this machine

`bundle_dmg.sh` drives Finder over Apple Events to lay the disk image
window out. The first attempt hung for four minutes on a system dialog:

> "claude" wants access to control "Finder".

The prompt was left unanswered — granting an application Automation
access is a system security setting and not something a build step should
decide. The `.dmg` was skipped and the `.app` built instead, which is
what the dogfood run and the updater artifact actually need.

**To build a `.dmg` locally:** answer that prompt, or grant the terminal
Automation access to Finder under System Settings ▸ Privacy & Security ▸
Automation. CI is unaffected; GitHub's macOS runners have no such gate.

## Two things found that this package did not fix

**`TAURI_SIGNING_PRIVATE_KEY_PATH` is not honoured** by the CLI at this
version, despite being named in `tauri signer generate`'s own output. The
build failed with *A public key has been found, but no private key* until
the variable was set to the key's **contents**. The runbook and the
workflow both use the contents. This also proves the point of
`unsigned.conf.json`: with `createUpdaterArtifacts` on and no key, the
build fails — so CI's nightly bundle had to opt out of updater artifacts
or it would have started failing tonight.

**The Settings tab does not scroll from the keyboard.** `.page-settings`
is `overflow-y: auto`, so a trackpad works, but the container never takes
focus, and Page Down after clicking in the page does nothing. A
keyboard-only reader cannot reach the About section at the default size.
This predates WP 1.12 — it arrived with the Settings tab in WP 1.9 — and
it is filed rather than fixed here.
